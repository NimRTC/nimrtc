## 1. Motivation

v0.10.3 is the final P1 patch — the patch train is sealed.
Three structural preconditions for P2 are now met:

1. **PAL Slice 1/2/3** (ADR-009) landed across v0.10.0–v0.10.3: engine
   resolves audio3a / codec / video_codec through `pal::*` seam; the
   `kDefaultRegistrars[]` table backs `register_all_default_plugins()`;
   `NIMRTC_PLUGIN_ID()` macro enables compile-time id validation.
   The assembly Profile library can now be backend-agnostic.
2. **ADR-010** (JSON Profile first-class): `profiles/*.json` are pinned
   as schema v1.0. The Profile library officialisation in v0.11.0 extends
   to all five profile variants.
3. **T-PAL Slice 7.5** (transport-selection.md §12.5): `WebRtcClassicStack`
   + `WebRtcClassicStackFactory` are registered; engine does not yet
   consume `ITransportStack*`, but the factory path and lifecycle are
   proven. Slice 4 (DTLS seam) lands in v0.10.x and is cleaned up in
   v0.11.0 via `EngineConfig::dtls_name`; Slice 5 (SCTP seam) is the
   intended v0.11.0 deliverable but is deferred to the v1.x
   WebTransport / QUIC re-design — see §2.2 and §10.

v0.11.0 ships the **Chrome media-interop** surface (audio + video
end-to-end, Case D PASS on Windows + Linux x86_64), PCM tap on WebRTC
APM, and the assembly Profile library. **DataChannel Chrome interop
(DC-1), L1 strict-priority scheduling across the DC plane (DC-2),
and the usrsctp production backend (TPAL-5) are explicitly
deferred** to the v1.x window — see §2.2 / §7 (the §7 fallback is
made permanent) / §10 (forward direction). P2 features that
require T-PAL Slice 6/7/8 (raw UDP bypass, Stack+Selector, engine
integration) remain deferred to v0.11.x patches or v1.x.

## 10. Forward direction: WebTransport / QUIC for v1.x

> **Status: placeholder.** The v1.x plan will be opened as a
> separate `docs/plan/v1.x-plan.md` once the v0.11.0 tag is cut.
> This section captures the rationale and the open questions so
> the v0.11.0 release notes can point at a clear forward path.

### 10.1 Why WebTransport, not SCTP-over-DTLS

- **Chrome is moving DataChannel to WebTransport.** Google's
  WebRTC roadmap (2023-onwards) explicitly deprecates the
  SCTP-over-DTLS path in favor of **WebTransport over QUIC**.
  `chrome://flags#web-transport` has been default-on since Chrome
  M114 (2023-05); the Chrome team's stated direction is
  "DataChannel future = WebTransport".
- **WebTransport is a Web standard.** The API is
  `ReadableStream` / `WritableStream` (WHATWG Streams), with
  bidirectional, reliable, and datagram-mode flows. PR-SCTP's
  "reliable + unreliable" duality maps to QUIC streams
  (reliable) + QUIC DATAGRAM frames (unreliable) — both are
  standard QUIC features, no in-stack PR-SCTP needed.
- **msquic is the natural cross-platform choice.** Microsoft
  maintains msquic (MIT-licensed), ships native Windows support
  via the kernel's QUIC APIs, supports Linux (kernel + userspace)
  and macOS. Cross-platform CI for msquic is a well-trodden
  path. (Alternatives: Cloudflare's quiche (Rust → CFFI) or
  Google's libquic (license is the deal-breaker).)
- **WebTransport over QUIC over DTLS over ICE** composes cleanly
  with the existing NimRTC stack — the DTLS layer above ICE
  (Slice 4) is the same DTLS, the ICE layer is the same libjuice
  ICE; the only new surface is the WebTransport / QUIC layer
  between DTLS and the application.
- **usrsctp's cross-platform build cost goes away.** 25 .c files,
  ~440 compilation units, the `tools/fix_usrsctp{1,2,3,4}.py`
  history (now deleted in v0.11.0) — none of that is
  needed under the WebTransport path.

### 10.2 v1.x plan scope (placeholder — to be opened post-v0.11.0)

- **Vendor selection** — msquic vs quiche vs custom. The
  decision criterion: cross-platform CI green (Win + Linux
  x86_64 + macOS + Linux aarch64), MIT-compatible license, no
  Rust / no CFFI / no FFI surface that violates the
  `src/plugins/` header-only invariant.
- **Seam surface** — `IWebTransportSession` (bidirectional /
  unidirectional streams + datagram frame API) replacing
  `ISctpSocket` for the data-plane use case. The `IDataChannel`
  facade stays; the IDataChannel implementations swap from
  `SctpDataChannel` to `WebTransportDataChannel`.
- **Engine integration** — DTLS keys (already extracted via
  `IDtlsSession::srtp_keying_material()` — same API the v0.11.x
  SCTP-over-DTLS placeholder was waiting for) feed into the
  WebTransport / QUIC layer; outbound WebTransport frames go
  out the DTLS transport; inbound DTLS frames feed into the
  WebTransport / QUIC layer.
- **DC-1 / DC-2 land** with the new backend. The Chrome
  e2e harness (`interop/chrome/test_chrome_datachannel.html` +
  `run_interop.py`) re-targets from "SCTP-over-DTLS m-line" to
  "WebTransport / QUIC a=transport" — same acceptance, new
  transport.
- **usrsctp removal** — `src/third_party/usrsctp/`,
  `src/usrsctp_socket.cpp`, `src/usrsctp_factory.cpp`, and the
  `UsrsctpSocket*` headers are deleted at v1.2.0 once the
  WebTransport path is proven. Expected LoC savings: ~3,500
  (including the vendored upstream).

### 10.3 Open questions for the v1.x plan

- **API stability commitment** — v0.11.0 remains experimental
  through v1.0; the v1.x plan needs to commit to a stable
  IDataChannel / IWebTransportSession surface by v1.0.0
  ("Beta 不再心虚", architecture §13 P3).
- **SFU track interop** — once DC-1 lands on WebTransport,
  DC-3 (DC forwarding policy) and BENCH-1 (sfu-relay benchmark)
  can be re-opened; both inherit the pre-1.0 decision window
  until then.
- **Chrome rollout** — WebTransport is default-on since
  Chrome M114, but the WebRTC-DataChannel-compat shim is
  still in place. When does the shim go away? Likely Chrome
  M130+ (mid-2025). v0.11.0 ships before that deprecation,
  so Chrome's compat shim still serves the data-plane use
  case for any v0.11.x out-of-tree caller that wires
  usrsctp manually.
