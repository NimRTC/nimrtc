## Summary

v0.12.0 is a **platform expansion + GMSSL TLCP DTLS backend +
named transport strategies** milestone on the v0.11.0 line:

1. **GMSSL TLCP DTLS backend（ADR-013）** — `DtlsSessionGmSSL`
   wraps GMSSL v3.x's GM/T 0044 (TLCP) handshake + SM2/SM3/SM4
   certificates + SM4-GCM encryption. Registered under id `"gmssl"` in
   `core::PluginRegistry::register_dtls_session()`. Engine default
   remains wolfSSL (zero regression); OHOS profile defaults to GMSSL.
   ADR-013 documents the decision rationale (GM/T 0044 TLCP over
   deprecated GM/T 0024; GMSSL not vendored; default cipher suite
   preserved for browser interop).
2. **OpenHarmony aarch64 CMake toolchain（Stage 0 ✅）** — Stage 0 of
   `docs/plan/openharmony-support.md`: `cmake/toolchains/ohos-aarch64.cmake`
   (dual-mode: real OHOS SDK cross clang + `--target` fallback),
   six OHOS CMakePresets.json presets (3 configure + 2 build + 1 test),
   and `cmake/NimRTCOptions.cmake` `if(OHOS)` musl-compat branch.
   Stages 1–4 remain in-progress; see §6.
3. **`nimrtc_link_gmssl()` CMake helper** — probes GMSSL v3.x
   `<gmssl/tls.h>` + `libgmssl` in `/usr/local`, `/usr`, and
   `$ENV{GMSSL_ROOT}`; does not depend on OpenSSL (GMSSL ships its
   own SM2/SM3/SM4 crypto primitives).
4. **`[updated 2026-10-12]` T-PAL Slice 7 / 7.6 / 8 — Named use-case
   transport strategies** (`docs/plan/transport-strategies.md`):
   five canonical strategies (`browser-call`, `teleop-ultra-low-latency`,
   `agent-gateway`, `sfu-relay`, `cross-network-peer`) named in PR1,
   implemented in PR2 alongside a real `raw-udp-arq` control stack,
   and wired into the engine + Profile loader in PR3. Each strategy
   pre-fills `TransportRequirements` so application code, Profile
   JSONs, and the registry refer to a strategy by id rather than
   reasoning about boolean flags at every call site.
5. **`[updated 2026-10-12]` Profile schema v1.1 (additive
   `transport` section)** — `profiles/schema/profile-v1.1.json`
   adds a top-level `transport` key to the v1.0 schema. v1.0
   profiles continue to load; the loader defaults the new section
   to `null` (= engine's compile-time default = `browser-call`).
   All nine existing JSON profiles have been retro-fitted with a
   sensible `transport.strategy` value (see transport-strategies.md
   §3).

Net source diff vs v0.11.0: ~2 400 lines across `src/transport/`,
`src/dtls/`, `src/engine/`, `src/modules/assembly/`, `profiles/`,
`cmake/`, `tests/`, `docs/`. Net new source files: 11
(`dtls_gmssl_session.cpp`, `dtls_gmssl_factory.cpp`,
`transport_strategy.hpp`, `raw_udp_arq_stack.cpp`,
`profile-v1.1.json`, etc.).

## Highlights

1. **`DtlsSessionGmSSL`** — `IDtlsSession` implementation using GMSSL
   v3.x TLCP (GM/T 0044, TLS 1.3-based). ~900 lines.
   Supports ECDSA P-256 + AES-GCM by default (matches browser suite);
   SM2/SM3/SM4 suites available by editing `cipher_priority` table.
2. **`GmSSLDtlsFactory`** — registers as id `"gmssl"`. Test-only accessor
   `get_gmssl_factory()` parallels `get_wolfssl_factory()`.
3. **`NIMRTC_ENABLE_DTLS_GMSSL` CMake option** — OFF by default.
   When ON: builds `dtls_gmssl_session.cpp` + `dtls_gmssl_factory.cpp`,
   defines `NIMRTC_HAS_DTLS_GMSSL=1`, links GMSSL.
4. **OpenHarmony aarch64 toolchain** — dual-mode
   `cmake/toolchains/ohos-aarch64.cmake`: OHOS SDK clang cross-compile
   (Mode A, recommended) + `--target=aarch64-linux-ohos` clang fallback
   (Mode B, for sanity checks without SDK). Six OHOS presets in
   `CMakePresets.json`.
5. **`docs/plan/ohos-audio-hal.md`** — Stage 4 output: OHAudio
   selected as the audio HAL for OHOS; OpenSL ES rejected (deprecated);
   integration plan for `OHAudioSource` / `OHAudioSink` adapter classes
   documented. Implementation is a v0.12.x patch follow-up.
6. **New documentation** — `docs/guides/building-on-openharmony.md`,
   `docs/guides/switching-dtls-backend.md`,
   `docs/api/engine_api.md`, `docs/api/engine_config.md`,
   `docs/plugin_author_guide.md`, `docs/troubleshooting.md`,
   `examples/demo-agent-gateway/README.md`.
7. **`[updated 2026-10-12]` Five named use-case transport
   strategies** (`docs/plan/transport-strategies.md`, PR1 + PR2 + PR3):
   - `browser-call` — 1:1 video/voice, browser interop required,
     `max_p99_ms = 200`, media + control ride `webrtc-classic`.
   - `teleop-ultra-low-latency` — robot / drone / vehicle teleop,
     `max_p99_ms = 50` on control, both planes use independent
     `raw-udp-arq` stacks (rule 2, two-stack prescription).
   - `agent-gateway` — server-side AI Agent pipeline; browser interop
     on media plane, `raw-udp-arq` on control plane for LLM/ASR
     traffic (rule 1b).
   - `sfu-relay` — SFU forwarding middlebox; `webrtc-classic` media,
     `null` control (no L2 data plane).
   - `cross-network-peer` — lossy / mobile / cross-ISP peer call;
     `webrtc-classic` with tighter `max_p99_ms = 150` (rule 1 variant
     not previously named in §5.3).
   Each strategy has a `kStrategy*` constant in
   `src/transport/include/nimrtc/transport/transport_strategy.hpp`
   plus a `strategy_by_name()` lookup that the Profile loader uses.
   Unknown strategy name throws `std::invalid_argument` with the
   list of valid ids.
8. **`[updated 2026-10-12]` Profile schema v1.1 (additive)** —
   `profiles/schema/profile-v1.1.json` adds a top-level `transport`
   key with `{strategy, media{...}, control{...}}` sub-blocks.
   All nine existing JSON profiles (`call`, `live`, `transport`,
   `agent`, `agent-gateway`, `agent-low-latency`, `teleop`, `sfu`,
   `sfu-agent`) are retro-fitted with a default `transport.strategy`
   value (see transport-strategies.md §3). v1.0 profiles continue
   to load; missing `transport` section defaults to `null` and
   falls back to the engine's compile-time default
   (`browser-call`-equivalent).
9. **`[updated 2026-10-12]` Engine integration + Profile bridge**
   (PR3): `EngineConfig::transport_strategy_name` (string) added
   alongside the existing `EngineConfig::transport_name`. The
   engine now (a) resolves the strategy name to a
   `TransportRequirements` via `strategy_by_name()`, (b) calls
   `CapabilitySelector::select()` to get a `TransportSession`
   with both `media_factory_id` and `control_factory_id`, and
   (c) records the chosen session in the engine's `open()` result
   for diagnostic + e2e-test inspection. **The factory is selected
   but not yet instantiated** — the existing
   `cfg.transport_name`-driven media-stack construction path
   remains in effect. Wiring the strategy's chosen
   `media_factory_id` / `control_factory_id` into a real
   `MakeTransportInstance()` call is a v0.13+ change (see
   "What's NOT in v0.12.0" below).
10. **`[updated 2026-10-12]` `raw-udp-arq` control stack registered**
    (PR2): the first non-`webrtc-classic` control-plane factory
    under `core::PluginRegistry::register_transport_stack()`.
    ID `"raw-udp-arq"`. Used by `teleop-ultra-low-latency` and
    `agent-gateway` to carry the high-frequency control channel
    independent of the media plane.
11. **`[updated 2026-10-12]` DTLS 1.2 forced for Case D Chrome
    interop** (commit `36ee838`, cherry-picked from
    `fix/windows-dll-boundary` → main): `dtls_wolfssl_session.cpp`
    no longer negotiates DTLS 1.3 by default. wolfSSL 5.9.2's
    DTLS 1.3 server has a broken short-circuit that both requires
    a `key_share` extension up front on a 1.2-style ClientHello
    from a 1.3-capable client (emits `missing_extension`,
    82ca051 disables DTLS 1.3 in unit tests) AND fails to
    reassemble BoringSSL's flight-1 ClientHello fragments in the
    NimRTC ↔ Chrome e2e (CI run 38057234934 — 18 RECV
    Handshake fragments, zero SEND, then close_notify warning).
    v0.12.0 forces DTLS 1.2 on both client and server paths to
    restore the Case D Chrome interop gate.

## What's NOT in v0.12.0 (explicitly deferred)

- **OHOS-aarch64 end-to-end audio capture** — OHAudio adapter
  implementation is a v0.12.x patch (Stage 4 output is this document).
- **OHOS ↔ Chrome / Firefox interop** — TLCP is not supported by any
  browser; OHOS ↔ NimRTC-Desktop uses wolfSSL path (set OHOS side
  `cfg.dtls_name = "wolfssl"` for browser interop).
- **GMSSL SRTP backend** — GM/T 0044 SRTP profile is P4; SRTP
  continues to use wolfSSL.
- **usrsctp on OHOS** — deferred to v0.12.x patch after 4-platform
  green; OHOS uses `SctpStubFactory` (id `"stub"`) for now.
- **T-PAL Slice 6** (Raw UDP bypass) — v0.11.x patch.
- **`[updated 2026-10-12]` §5.3 rule 2 actual media-stack
  instantiation** — PR3's `cfg.transport_strategy_name` resolves
  the strategy and records the chosen `media_factory_id` /
  `control_factory_id` in the engine's `open()` result, but the
  engine still constructs the media stack through the
  pre-PR3 `cfg.transport_name`-driven direct-constructor path.
  Wiring the strategy's chosen factory id into a real
  `MakeTransportInstance()` call (so that
  `teleop-ultra-low-latency` actually instantiates a
  `raw-udp-arq` media stack instead of `webrtc-classic`) is a
  v0.13+ cycle that touches the engine's media-stack ownership
  path. Tracked under
  `docs/plan/transport-strategies.md` §6 Open questions (the
  "rule 2 actual instantiation" item).
- **`[updated 2026-10-12]` `max_p99_ms` budget enforcement** —
  the Selector **records** each strategy's `max_p99_ms` on the
  `TransportSession` for e2e-test / monitoring consumption, but
  does not enforce it at engine `open()` time. A
  `StrategyValidator` that fails the engine `open()` if the
  chosen stack's measured p99 exceeds the declared budget is
  v0.13+ scope. Tracked under
  `docs/plan/transport-strategies.md` §6 #4.
- **`[updated 2026-10-12]` `cross-network-peer` naming
  review** — the strategy id is descriptive but long;
  alternatives (`robust-peer`, `lossy-link`, `mobile-friendly`)
  are tracked under `docs/plan/transport-strategies.md` §6 #1
  and deferred to a pre-1.0 naming review.
- **`[updated 2026-10-12]` Composite `sfu-agent` resolution** —
  the `sfu-agent` Profile JSON declares both SFU and Agent
  strategies on the same engine; the current loader cannot
  produce two `TransportSession`s for one engine. Options
  (two engines, second session slot, non-`strategy` field) are
  tracked under `docs/plan/transport-strategies.md` §6 #2 and
  deferred to the pre-1.0 decision window per v0.11-plan §7.
- **SFU-1 / DC-3 / BENCH-1** — pre-1.0 decision window per
  `docs/plan/v0.11-plan.md` §2.2.

## Compatibility / upgrade notes

- **Public API**: byte-identical with v0.11.0 except two additive
  fields on `EngineConfig`:
  - `dtls_name` (string, defaults to `""` → `"wolfssl"`) — added in
    the original v0.12.0 draft (TPAL-4).
  - **`[updated 2026-10-12]` `transport_strategy_name` (string,
    defaults to `""` → `"browser-call"`)** — added in PR3
    (`5f18e1a`). v0.11.0 callers that do not set
    `transport_strategy_name` continue to compile and behave
    identically.
- **Profile schema**: v0.12.0 adds an **additive** top-level
  `transport` key (`profiles/schema/profile-v1.1.json`). v1.0
  profiles continue to load unchanged; the loader defaults
  `transport=null` to the engine's compile-time default
  (`browser-call`-equivalent).
- **ABI**: Not committed; experimental through v1.0.0. Pin to a specific
  commit.
- **GMSSL builds**: `NIMRTC_ENABLE_DTLS_GMSSL=ON` requires GMSSL v3.x
  headers and library on the build host. Linux x86_64 and OHOS-aarch64
  are the supported hosts. Windows MSVC GMSSL builds are blocked by
  lack of pre-built GMSSL cmake targets on Windows; use Linux for
  GMSSL development.
- **No new third-party dependencies** for the default (wolfSSL) build.
- **No new tooling required.**
- **`[updated 2026-10-12]` Transport-strategy migration**: existing
  v0.11.0 callers that do not set `cfg.transport_strategy_name`
  continue to use the pre-PR3 `cfg.transport_name` direct-constructor
  path. The strategy is a **diagnostic + selection** change in v0.12.0
  (it records the chosen `media_factory_id` / `control_factory_id`
  in the engine's `open()` result) but does **not** alter which
  media stack is actually constructed. Real instantiation of the
  strategy's chosen factory id is a v0.13+ change.
