## 1. Motivation

v0.13.0 (= v1.0.0-alpha.1) closes the **API stability foundation**
cycle: every public header carries a stability marker, the
`NIMRTC_API_VERSION` macro set is in place, ADR-015 is merged, and
the P1 UAF-DTLS class is closed at the type-system level via
`std::weak_ptr<IDtlsSession>`. v0.13.0 makes **no progress on the
data plane** (per `v0.13-plan.md` §2.2 "Out of scope: DC-1 / DC-2 /
TPAL-5 — v0.14.x"; the v0.12.0 baseline
`test_datachannel_engine` 5/5 + `test_sctp_usrsctp` 4/4 continues
to be the in-process regression surface).

v0.14.0 is the cycle that **lands the missing data plane**. The
remaining blockers for v1.0.0 (per `v1.0-plan.md` §1) collapse to
two streams once API stability is in place:

1. **The data-plane wire (DC-1)** — `v0.11-plan.md` §2.2 + §10
   explicitly deferred the SCTP-over-DTLS path; the v0.14.x
   re-design is **WebTransport over QUIC**. The implementation
   path is split: alpha.2 lands the **seam** (no impl),
   beta.1 lands the **msquic-backed DataChannel + Chrome e2e
   Case E** (the v1.0.0 headline gate). This is the v1.0.0
   headline gate and the v0.14.x work proper.
2. **The pre-1.0 decision window is closed (2026-10-19, BDFL)**
   — §7 (SFU-1 / DC-3 / BENCH-1) is decided **NO**: SFU
   implementation is not a project core goal. v1.0.0 takes
   the `v1.0-plan.md §12.5` alternative path (skip
   `v1.0.0-rc.1`; ship v1.0.0 with the "stable API + DC-1
   land" baseline). SFU-1 / DC-3 / BENCH-1 defer to
   **v1.1.0** (the first post-stable cycle) and are
   explicitly out of v0.14.x scope. The "SFU-1 in v1.0.0
   conditional" wording in `v1.0-plan.md §7` is **retired**
   by this decision.

Plus three **supporting tracks** that ride the v0.14.x train:

3. **WebTransport / QUIC vendor decision (ADR-014)** — the
   `v1.0-plan.md` §10 placeholder (msquic vs quiche vs custom)
   moves to **Status: Accepted** at alpha.2 tag-prep. The
   spike validates the 5 evaluation criteria
   (license, no-Rust / no-CFFI, cross-platform CI green,
   Windows-first, active maintenance). **No source code lands
   for the vendor** — just the ADR + a spike-validation
   program under `interop/v0_14_msquic_spike/`.
4. **EngineConfig::datachannel_backend field** — additive
   string field on `EngineConfig` that selects between
   `"web_transport"` (default post-v1.0.0 final), `"sctp"`
   (v0.x compat), and the seam's id (for custom backends).
   Lands in beta.1 alongside the `WebTransportDataChannel`
   impl so v0.x callers that hard-code `"sctp"` continue
   to work.
5. **Per-symbol inline stability annotation** — the
   v0.13.0 sweep marked headers at the file level
   (`NIMRTC_API_STABLE` once per file). The v0.14.x
   follow-up annotates the 5-10 public symbols per header
   individually (so `static_assert(NIMRTC_API_STABLE(foo))`
   is a per-symbol check). Slip-or-land in v0.14.x;
   not DoD but lands if cycle time allows.

> **What v0.14.0 is NOT**: it is NOT a feature dump. v0.13.0
> ships the API stability framework; v0.14.x ships the data
> plane on top. **No new protocols beyond WebTransport / QUIC**
> (no SFrame, no MLS, no DTLS 1.3 enablement). **No new
> transport strategies** (the 5 named strategies from v0.12.0
> stay unchanged). **No new DTLS backends** (wolfSSL + GMSSL
> from v0.12.0 stay unchanged).

> **Why v0.14.0 = v1.0.0-alpha.2 + v1.0.0-beta.1 and not
> just v0.14.0**: the `v1.0-plan.md` §8 + §12.2 pre-release
> split makes this explicit. v0.14.x covers **two
> pre-release phases** — alpha.2 (the seam lands) and
> beta.1 (DC-1 lands) — because the v1.0.0 headline gate
> (Case E Chrome DataChannel) is a multi-month build that
> needs an interim seam-landed checkpoint. The cycle cuts
> **two Git tags**: `v0.14.0` (alpha.2; seam + registry +
> ADR-014 + CI green) and `v0.14.0-beta.1` (beta.1; msquic
> impl + DataChannel + Case E + header freeze). The
> marketing version stays anchored to the v0.x line until
> v1.0.0 final. `NIMRTC_API_VERSION_PRE_RELEASE` macro
> cycles `"alpha.2"` → `"beta.1"` between the two cuts;
> the CHANGELOG carries both `[1.0.0-alpha.2]` and
> `[1.0.0-beta.1]` sections (one per tag cut).

  msquic C API surface** (e.g. msquic's stream reset semantics
  are not expressible in the current `IBidirectionalStream`

  not after). If a method is fundamentally missing, the

### 9.2 Decision criteria (per `v1.0-plan.md` §10.2)

1. **License**: MIT / BSD-2 / Apache-2 only (no GPL, no SSPL).
2. **No Rust / no CFFI**: preserve the `src/plugins/` header-only
   invariant; no FFI surface that violates it.
3. **Cross-platform CI green**: windows-2022 + linux-gcc + macos-clang
   + linux-aarch64.
4. **Windows is first-class**: msquic's kernel-mode QUIC support
   is the differentiator; quiche is userspace-only on Windows.
5. **Active maintenance**: last commit within 6 months of v0.14.0
   tag cut.

### 9.3 Spike program structure

```
interop/v0_14_msquic_spike/
├── README.md                     # Documents the 5-criterion check
├── src/
│   ├── main.cpp                  # Bootstraps a MsQuicRegistration
│   │                             # + a MsQuicConfiguration + a
│   │                             # MsQuicConnection in 0-RTT mode
│   ├── echo_client.cpp           # 0-RTT echo client (round-trip
│   │                             # latency < 50 ms target)
│   ├── echo_server.cpp           # msquic listener; accepts the
│   │                             # 0-RTT resumption; echoes payload
│   └── stream_reset.cpp          # tests MsQuicStreamSendComplete
│                                 # + reset_stream semantics
├── CMakeLists.txt                # links against src/third_party/msquic/
└── results.txt                   # output: criterion 1-5 PASS/FAIL
                                  # with timestamps + commit SHAs
```

The spike output is the ADR-014 evidence: if any criterion
fails, the ADR reopens and falls back to quiche.

### 9.4 Provisional decision (per `v1.0-plan.md` §10.3)

**msquic** — MIT-licensed, native C / C++ API, Windows-first,
cross-platform CI green, no FFI / no Rust. The spike must
verify items 1-5 above; if any fails, fall back to **quiche**
(BSD-2, C API, userspace only) with the Windows story
documented as a v1.1.0 follow-up.

### 9.5 Fallback path (if msquic fails the spike)

If the spike shows any of:
- License is not MIT/BSD-2/Apache-2 → fall back to quiche.
- Rust CFFI is required (no C API) → fall back to quiche
  (Rust CFFI is a deal-breaker per `v1.0-plan.md` §10.1).
- Cross-platform CI is red on 2+ platforms → fall back to
  quiche (userspace; Windows story documented as v1.1.0).
- Windows is not first-class (kernel QUIC absent) → fall back
  to quiche (userspace; Windows story documented as v1.1.0).
- Maintenance is stale (last commit > 6 months) → fall back
  to quiche (more active upstream).

The fallback is **the same PR cycle** (the alpha.2 tag cut
holds; the spike re-runs with quiche; the seam headers and
registry slot are vendor-agnostic so the migration is a
`src/web_transport/src/web_transport_*_session.cpp` swap
plus a CMake change).
