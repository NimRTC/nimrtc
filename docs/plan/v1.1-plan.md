## 1. Goal

`v1.1.0` is one release that makes `v1.0.x` verifiable, consumable and
weak-network-tolerant. It does four things:

1. **Verifiable** — anyone can reproduce latency/jitter/throughput and
   weak-network numbers from `build/e2e/` and `build/weaknet/`.
2. **Consumable** — `cmake --install` yields `include/` + `lib/` +
   `lib/cmake/NimRTC/`, and `find_package(NimRTC)` resolves without a source
   build (fixes the `v1.0.2` known issue where bundles shipped only the
   vendored third-party stack).
3. **Hardened** — the transport-stack, media/RTP and DTLS residuals are closed
   and covered by tests.
4. **Differentiated on the public surface** — the `ref_frame` timeline map and
   the command-to-frame correlation are engine-level APIs, video statistics are
   engine-level observable, and the weak-network quality chain (Goog-CC BWE,
   unified adaptive jitter buffer, RTCP feedback loop) is in place.

Out of scope: SFU-1 / DC-3 / BENCH-1 SFU parts, new codecs, mobile bindings,
production deployment guarantees, SM4-GCM SRTP, `cloudgame` official Profile.

### Version numbering after this consolidation

- `v1.1.0` — this release (everything below).
- `v1.1.x` — **patch releases only**: bug fixes, security fixes and build
  regressions against `v1.1.0`. No new feature, no API addition, no
  behaviour change beyond the fix itself. See §5.6.
- `v1.2.0` — the next release after this one; the usrsctp removal already
  scheduled for `v1.2.0` (per `v0.11-plan.md` §2.2) stays where it is, and
  everything this plan defers to "a later version" is now written **`v1.2+`**.

## 5. Decision records

### 5.1 Version consolidation (2026-11-06, BDFL)

**Decision**: the former `v1.1` / `v1.2` / `v1.3` plan drafts are consolidated into
one `v1.1-plan.md` targeting **v1.1.0**.

**Reasoning**: all three drafts described a single unreleased body of work on
top of the published `v1.0.2`; none of them had a release cut, a tag or a
published artefact behind it. Numbering them as three consecutive versions
implied three releases' worth of roadmap without three releases' worth of
delivered versions, and made the version ladder look far ahead of the
reality. One release, one plan, one version target.

**Consequences**:
- Track identifiers are renumbered for uniqueness (see §2 preamble): the
  transport track became `Ts`, the DTLS items became `Dtls1–Dtls4`.
- Everything deferred beyond this release is written `v1.2+`.
- The usrsctp removal already scheduled for `v1.2.0` (`v0.11-plan.md` §2.2,
  ADR-015) keeps its version — `v1.2.0` is now simply the release after this
  one.
- The `## [1.1.0]` CHANGELOG section is still written only when the C-track
  closes; the consolidation does not cut a release.

### 5.2 `cloudgame` does not enter the official Profile set (2026-11-04, BDFL)

`cloudgame` **is not** part of the official Profile combination in this
release; it is deferred to `v1.2+`.
Reasoning: (a) the hardest of its four coverage items, "input↔render-frame
alignment", depends on the **rendering side** (Unreal / Unity etc.) supplying
render-frame timestamps — beyond the engine's capability boundary (the engine
does not bundle codecs, §13 codec row; GPU hardware encode and render-pipeline
integration are out of scope); (b) cloud gaming competes on end-to-end latency
plus a GPU codec pipeline, where NimRTC cannot form a provable difference;
(c) the remaining three coverage items (BWE high-bitrate mainline /
frame-level timeline / strict input priority) are already covered by the
`teleop` family plus T1/T2, so the marginal value is low; (d) the Profile
itself is cheap (JSON + constants + byte-level regression) — shipping it
"to be in the official set" would be a low-value promise.
Conclusion: **priority goes to AI Agent** (`agent` / `agent-gateway` /
`agent-low-latency` / `relay-agent`) **and embodied-AI teleoperation**
(reusing the `teleop` family, no new Profile) — the differentiators that
matter for those scenarios (raw PCM tap primitive, strict-priority DC,
`ref_frame` timeline) are inside the engine's capability boundary and already
have an implementation base. Remote-vehicle takeover (`takeover`) belongs to
P4 (dual link + dead-man) and is not in this release.

### 5.3 Scenario priority (2026-11-04, BDFL)

Main bets: **AI Agent** (4 Profiles already in the registry) and **embodied-AI
teleoperation** (`teleop` family reuse); `takeover` → P4; `cloudgame` → deferred.

### 5.4 GMSSL dependency shape (2026-11-04, BDFL)

GMSSL enters as a **submodule + default-OFF build + CI opt-in leg**.
Reasoning: (a) under an OHOS / aarch64 cross-compile, "install GMSSL on the
system" is not workable — that was ADR-013's motivation in the first place,
and requiring every downstream to build and install into a sysroot just puts
the integration burden back; (b) the repo already vendors wolfSSL / msquic /
libsrtp / libopus as submodules — GMSSL was the single exception, and that
inconsistency is itself friction; (c) ADR-013 decision 6 claims "consistent with
wolfSSL (wolfSSL is also not vendored)", and that premise is **outdated** —
wolfSSL *is* vendored as a submodule, so this is a correction of stale
wording, not a reversal of the decision.
Constraints: (a) the vendoring must first check the GmSSL v3 LICENSE text and
write it into `vendor.json` (a compliance action, not a formality); (b) keep
the default OFF so non-GM/T users pay no build-time or artefact-size cost;
(c) the X1 acceptance includes a Windows/MSVC compile plus
`test_dtls_gmssl_tlcp` PASS.

### 5.5 SRTP backend scope (2026-11-04, BDFL)

This release lands **only the SRTP backend seam**; the SM4-GCM SRTP
implementation is deferred to `v1.2+`.
Reasoning: (a) libsrtp does not support SM4 — SM4-GCM SRTP would require
implementing the RFC 3711 KDF derivation (PRF swapped for SM3), the keystream
and the auth tag, byte-identical with the peer; that is real cryptography
work whose effort is underestimated; (b) it violates D1 "no self-built
security-critical components" — a self-built implementation touching media
encryption invites security-audit pressure as soon as it is claimed; the
sane path is an existing implementation or an external contribution.
**Usability criteria (for public wording)**: GM/T compliance has three layers
— GM/T TLS on the signalling path (TLCP, GB/T 38636 / RFC 8998) is **out of
engine scope** (§10 table says "upper layer"); the DTLS GM/T suite (TLCP +
SM2/SM3/SM4) is **inside** the engine and is covered by X1; SRTP SM4-GCM is
**inside** the engine but is not implemented here. Most non-classified
enterprise/government projects can therefore land once X1 ships (media streams
normally ride the international suites), while projects that require
end-to-end GM/T — critical infrastructure, some automotive — wait for the
follow-up version of X2.
**Mandatory companion action**: the README's "GM/T cryptography ready" wording
must be narrowed to "**DTLS/TLCP covered, SRTP still on the international
suites**" — otherwise it misstates the compliance status to enterprise
customers.

### 5.6 Version ladder: what is `v1.1.x` and what is `v1.2.0` (2026-11-06, BDFL)

**Decision**: the compressed "v1.2" content does **not** go into `v1.1.x`.
`v1.1.x` is reserved for patch-level fixes on top of `v1.1.0`; everything
that adds behaviour ships in `v1.2.0`.

**The ladder**:

| Version | Content | Rule |
|---|---|---|
| `v1.1.0` | The release this plan describes (quality + packaging + hardening + quality line). | The only feature-bearing release in the `v1.1` line. |
| `v1.1.x` | Bug fixes, security fixes, build/toolchain regressions, documentation corrections. | No new public API, no new behaviour, no new dependency. Every change must be a fix for something that is *wrong* in `v1.1.0`. |
| `v1.2.0` | The next feature release: the first part of the video-pipeline rewrite (`docs/plan/video-pipeline-v2-plan.md` Part B: the feedback → BWE → pacing → rate-control closure, the encoder plug-in seam, the profile → mode table), **the audio pipeline's P0+P1 body (`docs/plan/audio-pipeline-dev-plan.md` WP-0 … WP-11 — the two plugin seams, the `audio_rx` module, the clock-driven receive path, the send-path fixes, the negotiation and SDP completion, the engine wiring, the RR + statistics, the capture timestamp, the P1 public SDK)**, the usrsctp removal (`v0.11-plan.md` §2.2), the SM4-GCM SRTP implementation (X2 deferred item), and whatever the soak/C-track evidence forces. | Anything that is not a fix. |
| `v1.3.0` / `v1.4.0` | The remaining video-pipeline stages (hardware codec negotiation, the codec plug-in contract for H.265/AV1, the rendering-side alignment work), and the audio P2 body (WP-12: DTX/VAD, device layer, A/V sync, G.711) in `v1.4.0`. | Same rule: features only. |

**Amendment, 2026-11-06 (BDFL)**: the earlier draft of the audio plan
proposed a separate `v1.3.0` for the audio body. The owner compressed the
ladder instead: the audio P0+P1 body ships in `v1.2.0`, together with the
video Part B, instead of pushing the audio work one release line out.
`v1.1.x` is unaffected — no patch release of the `v1.1` line may carry the
audio seam. The decision is recorded in
`docs/plan/audio-pipeline-dev-plan.md` §6.2.

**Reasoning**: (a) mixing a feature into `v1.1.x` would make the patch line
un-testable against a moving target — the whole point of a patch release is
that a user can take it without re-reading a migration note; (b) the
"compressed v1.2" content is by construction not finished work, and
shipping an unfinished feature under a patch number hides its maturity
from users; (c) the version ladder should track *delivered* versions, and
the video-pipeline rewrite is a multi-release effort with an explicit
owner-decision record (OD-1 / OD-2 / OD-3) and its own release mapping —
it does not belong in a patch line of an unrelated release.

**Consequences**: (1) `v1.1.0` is cut from this plan as written; (2) a
`v1.1.x` release may only be cut from `v1.1.0` plus fixes, and each fix
needs its own regression test; (3) the "deferred to `v1.2+`" markers already
used throughout this plan stay valid — `v1.2+` now means `v1.2.0` and
later, and the first of those is the video-pipeline rewrite.
