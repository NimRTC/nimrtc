## 0. Before touching anything

1. `git status --short` — **expect a clean tree**. The audio pipeline's
   plugin seams and the `audio_rx` module were committed on `main`
   before the tag was cut; they are the v1.2.0 body and are *not* in
   `release/1.1`. Do not discard, reset, or `git checkout` anything.
2. `git fetch origin --tags` — pick up the tag object and any
   post-tag commits on `main`.
3. `python tools/v11_status.py` — the gate snapshot, for the record.
4. `git tag -v v1.1.0` — the signature, for the record. If this
   disagrees with the watcher (the watcher said OK, this fails),
   **stop** and report: the tag is not what the gate requires.

If the watcher wrote `build/v11-watch/BAD_SIGNATURE` instead of
`READY`, the tag exists but is unsigned. That is release-blocking:
report it and do nothing else. Do not "fix" the tag by re-tagging
over it — the release manager decides that, per `RELEASING.md` §3.3.

## 1. Post-tag mechanics (`RELEASING.md` §3.4 steps 13–16)

These are the release manager's steps and they are ordered; do them in
order.

| # | Step | Reference |
|---|---|---|
| 13 | Merge `release/1.1` back into `main`. This merge is **not** a new release. | §3.4 step 13 |
| 14 | Open the PR `chore: post-release version bump` advancing `CMakeLists.txt` and `version.hpp` to `1.1.1-dev` on `main`, so `find_package(NimRTC)` cannot pick up an in-progress build as `1.1.0`. | §3.4 step 14 |
| 15 | Mark the GitHub milestone `100% complete`. | §3.4 step 15 |
| 16 | Announce: the GitHub Release (auto-created, pinned) and a Discussions thread for public releases only — not for `*-alpha.*` / `*-beta.*`. | §3.4 step 16 |

Everything above is a **release-management** action, not an
engineering one. Steps 13–16 touch `main` and GitHub; they are what
the user has to approve before they happen. Present them, do not
silently perform them.

**Step 13 is a regular merge, not a fast-forward.** `release/1.1` was
cut from `main` at `44fb9e7` and then received the v1.1.0
stabilisation fixes by cherry-pick, so its commits have different SHAs
from the ones on `main`. `git merge release/1.1` from `main` therefore
produces a merge commit whose content is the v1.1.0 tree. That is the
right outcome: `main` keeps the v1.2.0 audio body and gains the v1.1.0
fixes, and nothing is rewritten. Do not rebase `main` onto
`release/1.1` — the audio body is public history.

## 2. The first v1.2 deliverable

`docs/plan/v1.1-plan.md` §5.6 defines `v1.2.0` as carrying four
things:

1. the video pipeline rewrite, Part B of
   `docs/plan/video-pipeline-v2-plan.md` (feedback → BWE → pacing →
   rate control → encoder hand-off → observability → proof),
2. the audio pipeline's P0+P1 body (`docs/plan/audio-pipeline-dev-plan.md`
   WP-0 … WP-11),
3. the usrsctp removal (`v0.11-plan.md` §10.2),
4. the SM4-GCM SRTP implementation (the deferred X2 item).

### 2.1 What to start with, and why

**Start with the audio pipeline's WP-0 … WP-11 body.** The reasons are
concrete, not stylistic:

* It is the only item of the four that is **already in flight** —
  `src/plugins/include/nimrtc/plugins/audio_decoder.hpp`,
  `src/plugins/include/nimrtc/plugins/audio_receiver.hpp` and
  `src/modules/audio_rx/` are uncommitted work in the tree right now.
  Continuing it is finishing something already started; starting
  something else would leave a half-landed seam set behind.
* The plan gives it a dependency-ordered body with per-WP
  acceptance criteria, so "the next step" is answerable from the
  document rather than from judgement.
* The video pipeline's Part B is explicitly a **multi-milestone**
  body (M1–M7 in `video-pipeline-v2-plan.md` §B.2) whose first
  milestone (M1, the feedback ground) needs the engine's RTCP
  parsing and BWE plumbing — that is a larger, less self-contained
  piece of work than the next audio WP.

The usrsctp removal is a *cleanup* item with a dependency on the
WebTransport path being proven. **That precondition is now met**: the
WebTransport product route shipped in v0.15.0
(`specs/slices/v0-15-0-web-transport-product-route.md`, module at
`src/web_transport/`, Chrome Case E harness green). The removal
therefore becomes available as a v1.2 item — but it is a mechanical
deletion touching `src/third_party/usrsctp/` (274 tracked files) and
the `src/sctp/` module, and it should follow the audio body rather
than interleave with it.

### 2.2 The work packages in order

Read `docs/plan/audio-pipeline-dev-plan.md` §3 (the WP table) and
take the **lowest-numbered WP whose acceptance criteria are not yet
met**, in order. Do not take a later WP before an earlier one unless
the plan says the earlier one is blocked, and if it is, say so
explicitly instead of skipping it silently.

For each WP:

* implement it under the `AGENTS.md` L1–L7 constraints — `src/plugins/`
  stays interface-only, `src/modules/<name>/` stays self-contained,
  `src/engine/` orchestrates and includes no concrete module header,
  and no module exports global mutable state;
* land its tests with it (`src/modules/<name>/tests/` or `tests/`
  as the plan says);
* keep `ctest` green — the suite was **697/697 green** on this
  machine at the time this order was written.

### 2.3 What is *not* the first deliverable

The SM4-GCM SRTP implementation. `AGENTS.md`'s禁区 forbids building
security-critical components from scratch, and the v1.1 plan's own
note on that item says the sane path is an existing implementation or
an external contribution. Deciding *how* to obtain it is an owner
decision, not an implementation detail — raise it, do not start it.

## 3. Definition of "the first deliverable is done"

* The audio pipeline's WP-0 … WP-11 body is landed, each WP with its
  plan-mandated tests.
* `ctest` is green on Windows, and the CI matrix's four legs are green.
* `docs/plan/audio-pipeline-dev-plan.md`'s status lines are updated to
  match reality (the plan is the status record; leaving it stale is
  a defect).
* `CHANGELOG.md` carries the entries for what actually landed.

## 4. Rules for the woken agent

* Re-read the plans before acting; this document is an ordering, not
  a substitute for them.
* Respect `AGENTS.md` L1–L7 and the project-root cleanliness rule.
  Nothing at the repository root except the allowed files.
* If a step needs an owner decision (the §3.4 release-management
  actions, the SM4-GCM approach, a spec gap), **ask** — do not pick.
* Conventional Commits, DCO sign-off, English commit messages.
