## 1. Why this plan exists

`main` currently contains more *implemented* than *proven* capability. The v1.2.0
body — audio pipeline P0+P1, video pipeline Part B (feedback/BWE/pacing/ABR),
session capability, DataChannel, and remote-desktop M1–M4 — is merged, and the
Windows test suite is green. What is missing is the second half of the claim:
cross-platform compilation proof, activation of paths that are written but not
enabled (AEC, DXGI zero-copy, TURN/TLS), and the observability surface
(`getStats`) that a user needs in order to trust the engine at all.

Tracks E and S therefore close the v1.2.0 promise. Tracks Q and C define the two
following releases, each of which strengthens a dimension the current engine is
weakest in — respectively *resilience* and *reachability*.

**Sequencing note:** E2 before E1 — the manifest must be generated on a build that
at least *compiles* on all three platforms, otherwise the baseline encodes a
Windows-only view of the surface.  **Done in that order** (#71/#72, then the
manifest), and the manifest agrees with the count-based check on the same
header set.

**E2 — what landed.** The Linux CI leg now installs the leaf-adapter dev packages
and *asserts* that every adapter leaf was compiled in, rather than letting a
missing package silently skip a source file. Two rounds:

- **PR #71** — the X11, XFixes, PipeWire and EGL leaves. The first CI run of
  that PR failed on the `NIMRTC_VIDEO_SINK_HAS_EGL=1` assertion, which was
  exactly the point: the runner image ships no EGL dev package, so the
  assertion caught a path that would otherwise have been skipped.
- **PR #72** — the Wayland leaves (`wayland-client`, `wayland-egl`,
  `xdg-shell`, `linux-dmabuf`). Asserting these exposed that **the Wayland
  renderer had never been compiled on any build host**: `wayland-protocols`
  ships the protocol XML, but the CMake lookup searched for the *generated*
  header, so it never succeeded and ~20 branches of `egl_renderer.cpp` were
  dead code. Behind them were four real defects (a `wl_shm_pool_create_buffer`
  call with three arguments instead of six, whose `wl_buffer*` result was then
  used as a raw pixel buffer; a DMA-BUF import calling a protocol API that
  does not exist; two non-existent Wayland requests; a missing listener member).
  All four are fixed and the path now compiles with all six optional leaves
  enabled.
- **PR #76** — the input-injection leaves (XTest, uinput). Asserting these
  exposed that **the XTest injection backend had never been compiled on any
  build host**: `libxtst-dev` was not in the CI package list, so
  `NIMRTC_HAS_XTEST=1` was never defined and roughly 200 lines of
  `linux_input.cpp` — the whole X11 branch of the injector — were dead code.
  Compiling it surfaced two real defects: `XTestFakeRelativeMotionEvent`
  was called with `nullptr` as its fourth argument, but that parameter is
  the event *delay* (an `unsigned long` timestamp), not a pointer; and the
  module linked `libXtst` but not `libX11`, so the `XOpenDisplay` /
  `XFlush` / `XCloseDisplay` calls it makes through the extension were
  undefined at link time.  Both are fixed, and both the XTest and the
  uinput backends are now asserted in CI.
- **PR #78 — the Wayland sink presented nothing.**  E2 proved the Wayland
  leaves *compile*; running the sink against a headless Weston showed that
  neither presentation path had ever *presented* a frame.
  `init_egl()` left the EGL context bound on the `open()` thread, so the
  presenter thread's `eglMakeCurrent()` failed with `EGL_BAD_ACCESS` on every
  frame; `init_wayland()` committed the first buffer before the `xdg_surface`
  had been configured, which Weston treats as a protocol error and kills the
  client; and `draw_with_egl()` counted a failed `eglSwapBuffers()` as a
  presented frame.  All three are fixed; both the EGL and the `wl_shm` paths
  now present 1280x720 and letterboxed 320x180 streams under headless Weston
  with no protocol errors.

  Compiling the backend proved it *builds*; it did not prove it *works*,
  and it did not.  The XTest path was using the **uinput** path's
  vocabulary: `XTestFakeKeyEvent()` was called with the kernel's
  `KEY_A` (30) where the X server wants a **keycode** — the number it
  assigned to a physical key on the *active* layout — and
  `XTestFakeButtonEvent()` was called with the kernel's `BTN_LEFT`
  (`0x110`) where it wants a **button number** (`1` = left).  The two
  schemes are unrelated, so the server injected *nothing* while the
  injector reported success.  The X11 vocabulary (KeySyms and button
  numbers) is now kept apart from the kernel's, and the KeySym is
  converted to a layout-aware keycode with `XKeysymToKeycode()` at the
  call site.  Constructing the injector also crashed the process:
  `XTestQueryExtension()` writes to **all** of its out-parameters, and
  the call passed `nullptr` for each of them.

  The two tables live in a portable header (`src/linux_input_codes.hpp`)
  that carries no platform type, so the unit test verifies all of them
  on every CI leg — including the Windows one, where the Linux backend
  is never compiled.

macOS (ScreenCaptureKit, Metal) is covered by the existing `macos-clang / arm64`
leg, which compiles the whole tree including the Objective-C++ renderer.

**E1 — what landed.** The API surface is now pinned by a *set*, not a *count*.

`tests/test_api_classification.cpp::total_header_count_matches_baseline` asserted
that the number of public headers equalled a baseline constant.  A count cannot
tell a swap from a change: deleting `a.hpp` and adding `b.hpp` in one PR leaves
the count untouched, so CI stayed green while the public surface had moved.
ADR-015 calls that surface a contract, and a contract needs the actual list.

`docs/api/public_headers.manifest` is that list — one path per line, sorted,
`/`-separated, relative to the repo root.  `scripts/check_api_manifest.py`
compares it against the tree and names both sides of a drift (the headers that
appeared, the ones that went away).  It is wired into all four platform legs of
`ci.yml` and into `ci-fast`.

The manifest and the existing count check agree on the selection rule, so the
manifest is a strict refinement of the old gate rather than a second,
differently-scoped surface.

> **The baseline is now 189, not 191.**  The list was cut at 191 when the
> freeze landed; E7 then removed the two `@deprecated` `usrsctp` headers, so
> the current count is **189** (see the E7 block below).  The *rule* is
> unchanged — only the membership moved — which is exactly the kind of
> change the manifest makes visible and the old count-only gate would have
> hidden: deleting two headers and adding two others in one PR leaves the
> count at 191.

**E3 — what landed, and what the rig had to get right.**  The row said "vendored
APM enabled by default on at least one platform, with an ERLE measurement
recorded".  Two halves, and the *measurement* half was the expensive one: the
repository had no way to measure ERLE at all.

Getting a number required three things, in this order:

1. **A buildable vendored APM.**  The APM is pre-built via Meson, and the
   Windows build script was **broken in two ways**.  It passed
   `--cpp-args=/Zc:designated-initializers` to `meson setup`, which meson
   1.11 rejects outright (`unrecognized arguments`) — the flag has to travel
   in a *native file* instead.  And the script assumed a clean MSVC
   environment, which an earlier revision of the script broke by putting the
   PATH override on the same command line as `call vcvars64.bat`: cmd expands
   the whole line *before* executing it, so `%PATH%` was substituted with the
   pre-vcvars value and the MSVC toolchain was dropped from the environment
   altogether.  Both are fixed in `tools/build_webrtc_apm.cmd`.

2. **A rig with a *known* echo path.**  A physical loudspeaker→microphone
   loop is not reproducible and needs audio hardware, so the rig synthesises
   one: a render signal, a pure 20 ms delay, and that delay reported to the
   canceller through the same `Config::aec_delay_headroom_ms` a host would
   use.  The render signal is **speech-like broadband noise**, not a tone —
   the canceller's delay estimator rejects periodic signals, so a tone would
   have produced an ERLE that no real session reaches.  The capture segment
   carries **echo only**, so `ERLE = 10·log10(P_uncancelled / P_cancelled)`
   needs no near-end/echo separation.

3. **A near-end check that is not fooled by the rig.**  The ERLE number alone
   would also pass if the canceller simply muted the microphone.  The first
   attempt used a *broadband* near-end talker and **failed** — because the
   upstream APM's residual echo suppressor attenuates it, correctly: a
   broadband near-end signal is statistically indistinguishable from the
   residual echo the suppressor exists to remove.  The fix was to measure the
   near-end as a **tone** at a frequency the echo path does not carry, which
   a single-bin DFT can separate from the echo.

The result, on **Windows / MSVC / x64** and on **Linux / GCC 11 / x86_64**:
**ERLE = 30.3488 dB** (echo power 0.0185 → 1.71e-05), against the 15 dB floor
ITU-T P.807 sets for a converged canceller in a stationary synthetic path; the
near-end tone keeps 80% of its amplitude; and a control run with the canceller
off reports 0.0 dB, which is what proves the number comes from the canceller
and not from an artefact of the rig.  The two platforms read **bit-identical**
values, because the rig's input is deterministic (an xorshift32 source) and
the canceller converges to the same residual on the same input.

Two limits are worth stating plainly.  The measurement covers **two** of the
three shipping platforms — the vendored APM's macOS / Apple-Clang build path is
still unverified, so a third reading is missing.  And the synthetic path is
**delay-only, with no multipath**, so a real room will measure lower.

**The "enabled by default" half is now asserted in CI**, which it was not
when the measurement landed.  Every CI leg configured with
`-DNIMRTC_VENDORED_WEBRTC_APM=OFF`, so the option's *default* was asserted
nowhere: flipping it to OFF in `cmake/NimRTCVendored.cmake` would have left
the whole matrix green while shipping the stub 3A.  A dedicated leg
(`linux-apm / real 3A`) now prebuilds the real APM, configures with the option
**left at its default** — no `-D` flag at all — and runs the rig under
`NIMRTC_REQUIRE_WEBRTC_APM=1`.

That last part is the subtle one, and it is worth stating because a *skip* is
a *pass* to CTest: if the APM silently degraded to the stub, the three ERLE
cases would skip and the leg would report green **while measuring nothing**.
`NIMRTC_REQUIRE_WEBRTC_APM=1` turns that skip into a failure.

Building that leg on Linux also exposed a real portability defect in the rig:
`RecordProperty` takes an `int`, and passing a `double` is rejected by GCC's
`-Werror=float-conversion` (MSVC does not complain).  The measurements are now
scaled explicitly and recorded as `<name>_x1000`.

The full numbers, the reproduction commands and the method live in
`docs/interop/aec-erle-results.md`.

**E4 — what landed, and the bug it uncovered.**  The row said "re-run Case E";
the interesting part is that **Case E had never passed on either plane**, and
the failure was not in NimRTC's protocol code.

Two things were wrong, and they compounded:

1. **Case E was never asserted.**  `interop.yml` had a step named
   `Provision WebTransport TLS material` — it generated the certificate and
   stopped there.  `tools/run_e2e_acceptance.py` has implemented
   `run_case_e_dtls()` and `run_case_e_webtransport()` all along, but the
   orchestrator's `--case=all` deliberately excludes them, so **nothing in CI
   ever invoked them**.  A broken Chrome interop could not turn CI red.

2. **The WebTransport plane could not have passed.**  The certificate script
   put the self-signed certificate into `Cert:\CurrentUser\My` — the
   *personal* store, which is where msquic loads it from, so the **server**
   was always fine.  But the client validates the *chain*, and a self-signed
   certificate is its own issuer: unless that exact certificate is trusted,
   it is an unknown root and the handshake dies with
   `QUIC_TLS_CERTIFICATE_UNKNOWN` (alert 46).  `--ignore-certificate-errors`
   does not rescue it, because Chromium's QUIC proof verifier rejects a
   successful verification whose issuer is not a known root anyway.

The fix follows the mechanism the DTLS plane of the same case already uses:
publish the certificate's **SPKI SHA-256** and hand it to Chrome via
`--ignore-certificate-errors-spki-list`, which pins the trust decision to
exactly this certificate's public key.
`scripts/generate_wtserver_cert.ps1` writes the hash to
`build/wtserver_spki.b64`; the WebTransport harness passes it to Chrome.

Installing the certificate into `Cert:\CurrentUser\Root` was the obvious
alternative and it was tried first — and it **hangs on a non-interactive
runner**: the protected-root store raises a confirmation dialog that nobody
can answer on a GitHub Actions runner, so the script never returns and the
job dies at its timeout.  (It works from an interactive desktop, which is
what makes it so easy to get wrong: it passed locally and hung on CI.)  It
would also change the trust decisions of every other program on the machine
for the lifetime of a test certificate.  The SPKI allowlist touches no
machine state at all.

With that, **both planes pass**:

- **DTLS-only** — Chrome `dtlsState === 'connected'`, SRTP cipher
  `SRTP_AES128_CM_HMAC_SHA1_80`, and NimRTC's own
  `engine[dtls→srtp]: DTLS reached Connected` plus a `CLIENT_RANDOM` in the
  wolfSSL keylog.  Three consecutive runs, no flake.
- **WebTransport** — session ready, datagram echoed
  (`NIMRTC-WT-DGRAM-ECHO-01`), bidirectional stream echoed.

CI now runs both planes as **assertions**: a failure in either fails the job.
The results, the reproduction commands and the full root-cause write-up live in
`docs/interop/chrome-interop-results.md`.

One caveat that is worth stating plainly, because it is a *scope* limit rather
than a defect: the browser-interoperable `RTCDataChannel` plane (remote-desktop
plan **G1b**) is **not** covered.  The SCTP data plane is its own story —
`datachannel_backend = "sctp"` is rejected by `engine_transport.cpp` with a
hard error and the default `sctp_socket_name` is `"stub"`, so the browser-side
`RTCDataChannel` interoperability was already off the table before this row.
That needs its own decision, not something this row silently absorbed.

**E7 — what landed, and why the row was smaller than it read.**  The plan
first wrote E7 as "write an in-tree SCTP stack, then delete the vendor tree",
which would have made it the schedule driver of M0.  That reading was wrong,
and the correction is the interesting part of this row.

The SCTP data plane was **already** retired from the *public* selector in
v1.2.0 (WP-A / DEC-4 = A1): `datachannel_backend = "sctp"` is rejected by
`engine_transport.cpp` with a hard error, and the default `sctp_socket_name`
is `"stub"`.  `nimrtc::sctp::register_default_plugins()` has published only
the `"stub"` factory since v0.11.0 — the `"usrsctp"` factory was *never* in
the registry on `main`.  So there was no in-tree SCTP stack to write: what
remained was a **deletion** of unreachable code that the build still paid for
on every platform.

What the change removed:

- `src/third_party/usrsctp/` — 269 files, ~5.5 MB — and the
  `nimrtc_vendor_usrsctp` target (plus its `install()` and
  `find_library()` entries in `NimRTCInstall.cmake` / `NimRTCConfig.cmake.in`).
- `usrsctp_socket.cpp` / `usrsctp_factory.cpp` and their two `@deprecated`
  public headers.
- `tests/test_sctp_usrsctp.cpp` — the in-process loopback regression.  It
  only ever ran on Linux (the `usrsctp_connect()` handshake never completed
  on Windows or macOS, so those platforms skipped it), and the backend it
  exercised no longer exists.
- `SctpDataChannel`'s production constructor's `get_sctp_socket("usrsctp")`
  lookup, replaced by `"stub"` — the only registered SCTP id.  The channel is
  now a well-defined "no data plane" channel (every send returns
  `kErrNotReady`) rather than a null-pointer one.

What it deliberately did **not** change:

- The `ISctpSocket` / `ISctpSocketFactory` seam.  The production data plane
  is WebTransport over QUIC (msquic), which never went through this seam.
- The `"sctp"` DataChannel factory's registration: it stays in the registry
  as the in-tree reference implementation for the DCEP codec and the PR-SCTP
  semantics.  What is retired is the *public selector*, not the backend.

The public header set shrinks from **191 to 189**.  Per D-N6 the manifest and
the count-based gate are regenerated in the same PR, and the PR names the two
headers it removes.

**Sequencing (D-N6).** Track S lands **after** the E1 manifest freeze, not
before it.  The manifest gate now exists to *catch* an undeclared public
surface, so freezing it before Track S adds public fields would either block
the work or train people to regenerate the manifest without thinking.  Instead:

- Every Track S row that adds a public symbol (S1's `snapshot_time_us` /
  `StatsDelta`, S2's inbound entry type, S5's candidate-pair entry) **must**
  come with an explicit `scripts/check_api_manifest.py --write` regeneration in
  the same PR, and the PR description must name the symbols it adds.
- The regeneration is not free: it is the *review surface*.  A manifest diff
  that adds a public type is a contract change, and the reviewer reads it as
  such — which is exactly the property the old count-based gate lacked.
- This supersedes the earlier sequencing note ("Track S consumes Track E's API
  baseline, so any new public field lands before E1 freezes the manifest").

### Execution order for M1 (the remaining v1.2.0 work)

M1 is gated on 4 Track E rows and 6 Track S rows.  The rows are not
independent, and the order below is the one the *dependencies* imply, not
the one that is easiest to start.  Each step names what it unblocks.

**Wave 1 — independent, start all three in parallel.**  Nothing here
depends on anything else in M1, and each one is self-contained.

| Step | Why it is first |
|---|---|
| **S1** (stats registry + snapshot lifecycle) | It is the *foundation* of the rest of Track S: `snapshot_time_us` / `StatsDelta` are what a per-stream entry hangs off, and what lets a host compute an interval rate. Every S2/S4/S5/S6/S7 entry is easier to add once there is a registry to register it in. It also adds public fields, so it is the row that pays the D-N6 manifest-bump cost first — better to pay it once, early, and learn the process on it. |
| **E6** (saturated-link G2 benchmark) | The heaviest *evidence* item, and the one with the longest wall-clock: a saturation benchmark has to hold a link at capacity long enough for ABR to react. Starting it first means the measurement is running while everything else is built. It needs no code change to the engine. |
| **E3** (AEC activation + ERLE) | Depends on getting a *measurement rig* right (a loopback that produces a known echo path), which is setup work, not engine work. It is also the row most likely to slip on quality grounds, so starting it early leaves room to fail and retry. |

**Wave 2 — after S1 lands.**  These four each add a per-stream or
per-object entry, so they are cheapest once the registry exists.

| Step | Depends on |
|---|---|
| **S2** (inbound RTP per-SSRC) | S1 — the outbound side already has `VideoStreamStats`; the inbound side needs the same shape. |
| **S4** (audio per-stream) | S1 — the audio counterpart of `VideoStreamStats`. |
| **S5** (ICE/DTLS/SRTP transport stats) | S1 — candidate-pair entries and RTT need a registry and a snapshot timebase. **This is also the precondition C4 depends on**, so it is on the critical path to v1.4.0, not just to M1. |
| **S6** (DataChannel stats) | S1 — the same entry shape as the others. |

**Wave 3 — after S1 lands, but can run alongside wave 2.**

| Step | Depends on |
|---|---|
| **S7** (remote-desktop capture/encode/decode breakdown) | S1 — plus the `rd_qoe` collector, which is a separate module and the one piece of this row that needs its own implementation rather than wiring. |

**Wave 4 — the two that gate the tag itself.**

| Step | Depends on |
|---|---|
| **E5** (DXGI zero-copy) | Nothing in M1, but it is **driver-specific**: the row's own done-when allows a documented fallback, and the risk table says to accept staging readback as a fallback if a driver cannot do GPU-to-GPU. ## 6. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| macOS/Linux CI runners unavailable | E2 blocks; E1 baseline is Windows-only | Treat runner provisioning as the first task of M0; failing that, land compile-only Docker jobs for Linux and defer macOS with an explicit note |
| AEC activation regresses audio quality | E3 slips into v1.3.0 | **Resolved by measurement:** the gate was the ERLE number, not "it compiles". The rig measures **30.35 dB** (identical on Windows / MSVC and Linux / GCC 11) against ITU-T P.807's 15 dB floor, plus a near-end-survival check (the near-end tone keeps 80% of its amplitude) and a control run that proves the number comes from the canceller and not from the rig. A dedicated CI leg (`linux-apm / real 3A`) now re-measures it on every PR, with `NIMRTC_REQUIRE_WEBRTC_APM=1` so a silent fallback to the stub 3A fails the leg instead of skipping it. See `docs/interop/aec-erle-results.md` |
| DXGI zero-copy publication needs driver-specific paths | E5 slips | Accept staging readback as a documented fallback and record which GPUs take which path |
| Stats surface churn after freeze | E1/S8 conflict | **Resolved by D-N6:** the freeze already happened; every later public field is an additive, reviewed manifest bump in the same PR. The risk is now *silent* drift, which the manifest diff makes visible at review time |
| E7 assumed an in-tree SCTP stack that does not exist | E7 (and therefore M0) slips | **Resolved by inspection:** the SCTP data plane was already retired from the public selector in v1.2.0, and the `"usrsctp"` factory has not been in the registry since v0.11.0. E7 turned out to be a *deletion* task, not a "write a stack" task — **it landed**; see the E7 block above |
| TURN/TLS handshake scope creep (auth mechanisms, long-term credentials) | C1 balloons | Restrict C1 to the RFC 5766 long-term credential mechanism; leave alternative auth to a later ADR |
