## 0. What v1.2.0 handed us, and what it did not

The v1.2.0 body is *implemented and proven* on the axes it set out to cover:
cross-platform compilation, the AEC's measured ERLE, the DXGI zero-copy
path, the saturated-link G2 benchmark, and the complete stats surface
(145 documented fields, derived from the header and gated in CI).

What v1.2.0 does **not** claim is that the engine degrades *gracefully*
under a hostile network. That claim lives in the items below. Q1–Q5 were
written down in the v1.2 plan's Track Q row and are reproduced here
verbatim so the scope cannot drift; Q6/Q7 (added 2026-11-18) come from the
area plans that already scheduled them for this release.

| ID | Item | v1.2 plan's rationale |
|---|---|---|
| **Q1** | R2 — parameter-set mid-stream switch (H.264/H.265) | Resolution changes currently require an IDR; real callers change resolution mid-call |
| **Q2** | R4 — bounded memory under decode overrun | A slow or malicious peer must not be able to grow decoder queues without limit |
| **Q3** | T1 — RTX (RFC 4588) | Loss recovery today depends on PLI storms, which are both slow and expensive |
| **Q4** | T2 — PLI/FIR rate limiting | Bounds the cost that Q3 does not remove; prevents feedback amplification |
| **Q5** | Long soak across NAT + netem | 24h+ runs with reordering, loss, and jitter; the only credible robustness evidence |

**Q6 and Q7 were added on 2026-11-18**, when this plan was reviewed against
the *area* plans it draws from.  Both were already scheduled for `v1.3.0`
by the documents that own them and were missing here — the survey in §1
found them the same way it found the two defects in Q1 and Q2.

| ID | Item | Where it was already scheduled |
|---|---|---|
| **Q6** | R3 — render clock + A/V sync (the **video** half) | Originally targeted at `v1.4.0` by `docs/plan/video-pipeline-v2-plan.md` §B.1; the audio half shipped in `v1.2.0` (audio plan WP-14), leaving the video half the odd one out.  See §1.6. That document's release map now follows this one. |
| **Q7** | O-6 — end-to-end hardware encode on the CI matrix | `docs/plan/video-pipeline-v2-plan.md` Track X names **`v1.3.0`** as O-6's target.  It is a *coverage* item, not a feature: the hardware path is validated manually today, and the software path is what CI enforces. |

**Exit bar for v1.3.0** (v1.2 plan §3, extended): *Q1–Q7 all closed, soak
runs green, no regression in Track E/S acceptance.*

## 1. What the tree actually looks like today

This section is the **survey** that the plan is built on. Every claim here
was checked against the tree, not against a status field — the same rule
the v1.2 plan applied to its own Track E / Track S verification pass.

### 1.1 Q1 (R2) — parameter-set mid-stream switch: **the sender side exists, the receiver side does not**

The *sender* already does the right thing. `openh264_encoder.cpp`'s
`set_params()` re-creates the encoder when the geometry changes, and the
comment says exactly why:

```cpp
// A geometry change is a parameter-set change (B13).
//
// The peer's decoder is holding parameter sets that describe
// the *old* geometry.  The new ones have to travel with the
// new frame, or the peer cannot decode it until it asks for a
// keyframe (and, on a plain H.264 stream, may not even then).
```

So the new SPS / PPS travel with the next IDR. **The receiver is where
the gap is.** Two facts from the survey:

* `h264::StubDecoder::decode()` walks the Annex-B bitstream and reads
  `parse_sps()` — but only to fill `out.width` / `out.height` on the
  *output struct*. It never updates a decoder context, because it is a
  stub that produces no pixels. The **real** decoder (`Openh264Codec`,
  which links the vendored `ISVCDecoder`) takes its geometry from the
  bitstream's own parameter sets — which is the correct behaviour — but
  **nothing in the tree asserts that a mid-stream parameter-set change
  is handled without a restart**.
* The engine's own receive path decodes into **codec-owned** buffers
  (`video_codec_->decode(enc, raw_out, nullptr)`), so the engine has no
  geometry to re-initialise. The decoder is the sole owner of "do my
  parameter sets still match?" — and no test asks it that question.

**The missing thing is therefore not a mechanism; it is an assertion.**
A mid-stream resolution switch already works (the decoder is fed the new
SPS in-band and OpenH264 handles it); nobody has *proven* it. Q1 is
"write the test that fails on the pre-change code, and fix whatever it
finds".

The honest risk: OpenH264's behaviour on a mid-stream SPS change may
*not* be a clean re-init, and the test may reveal a real defect. That is
the point of writing the test.

### 1.2 Q2 (R4) — bounded memory under decode overrun: **the config exists, the enforcement does not**

This is the sharpest gap in the survey, and it is a *bug*, not a missing
feature:

* `jb::Config::max_packets` is declared in
  `src/modules/jb/include/nimrtc/jb/jitter_buffer.hpp` with the comment
  *"Hard cap on buffered packets (FIFO trim from oldest when exceeded)"* —
  and **`jitter_buffer.cpp` never reads it**. A search for `max_packets`
  across the whole tree finds the declaration, one test that asserts the
  *config value* round-trips (`test_jb.cpp:57`), the plugin adapter that
  hard-codes `c.max_packets = 512`, and **no enforcement anywhere**.
* The audio jitter buffer's `frame_buffer_` is a `std::map` keyed by RTP
  timestamp that only ever shrinks in `pop()` / `flush()`. A peer that
  sends a *new* timestamp every packet and never lets a frame become
  playable grows that map without limit.
* The *video* jitter buffer (`video_jb`) **does** enforce a bound —
  `max_inflight_frames` (default 8), with an eviction policy that prefers
  dropping an incomplete frame over a complete one. That is the right
  shape, and it is the model for the audio side.

So Q2 is: **make the declared cap real on the audio path, and prove the
memory is bounded under a sustained overrun** (not merely that the
config value survives a round-trip).

### 1.3 Q3 (T1) — RTX (RFC 4588): **not started** *(at the time of the survey — now closed, see §3 Q3)*

The survey found **no RTX anywhere**: no `rtx` payload type, no
`a=rtpmap` entry with an `apt=` (associated payload type) parameter, no
`fmtp` line carrying `apt=`. What exists instead is the *v1.1 Q3*
mechanism, which is **not** RTX:

* The sender keeps a **retransmission ring** (`rtx_cache`, bounded by
  `cfg.retransmit_cache_packets`) of the most recently sent packets.
* A NACK asks the sender to repeat a packet; the sender **re-sends the
  original packet** — same sequence number, same payload type.

RFC 4588 §4.1 is explicit that this is *not* RTX: a retransmission
"SHALL be sent on a different payload type" so the receiver can
distinguish it from the original and restore the original sequence
number. The v1.2 plan's T1 row says exactly this: *"Today NACK is
answered by re-sending the original packet, which is not RTX."*

**The consequence that makes Q3 non-trivial**: switching the
retransmission to a real RTX payload type means the receiver must
*un-RTX* — unwrap the RFC 4588 header, restore the original sequence
number, and splice the payload back into the frame it belongs to. The
receiver's frame assembly is keyed on the **original** sequence number,
so an RTX packet arriving under a *new* sequence number would otherwise
be treated as a new packet of a new frame.

The good news: the survey found the machinery this needs. The sender
already has a bounded retransmission cache, the receiver already has
frame reassembly, and the SDP writer already emits `a=rtcp-fb` lines.
Q3 is the *protocol* work on top of three working halves.

### 1.4 Q4 (T2) — PLI/FIR rate limiting: **partly landed, the feedback *amplification* half is missing**

The survey found the limiter exists and is well-built:

* `video_pipeline::KeyframeLimiter` (remote-desktop plan B14) — a
  min-interval gate, a key-frame **cost budget**, and a hard cap per
  window, wired around the `FirCoalescer` (RFC 5104 §4.3.1.1). It sits
  on the **sender** side: "may the encoder produce a key frame now".
* The engine's own `request_keyframe_on_decode_failure()` has a **250 ms
  throttle** — the **receiver** side: "may I ask for a key frame now".
* The engine counts every feedback by type
  (`video_feedback_rx_{pli,fir,nack,…}`, `video_feedback_tx_{pli,nack}`).

So the *rate* is bounded on both ends. What is **not** bounded is the
*amplification*: the receiver's PLI request travels through
`queue_video_feedback()` → `pending_video_feedback_` → `flush_video_feedback()`,
and the pending report is **merged** rather than counted. The receiver
also has no bound on how many **NACKs** it emits: `pending_nacks` grows
with every detected gap and is drained into one RTCP packet without a
cap.

That is the T2 gap the video plan's T2 row names: *"the receive side
stops asking for keyframes it cannot get"*, plus *"No IDR storm under a
sustained loss profile; asserted over a 30 s synthetic-loss run."*
Q4 is the **receive-side** half: a bound on the feedback the receiver
emits, and a 30 s synthetic-loss assertion.

### 1.5 Q5 — long soak across NAT + netem: **the tooling exists, the window does not**

`docs/plan/soak-runbook.md` is a complete operating procedure for a
**7-day** acceptance window, with `tools/run_soak.py` (the collector, with
a self-test), `tools/fetch_soak_evidence.py` (the artifact fetcher), and
a scheduled `.github/workflows/soak.yml`. That procedure measures
**Case D and Case E** — the Chrome interop and the harness acceptance.

What it does *not* do is what Q5 asks for: **impair the network**. The
runbook's own window is a *clean-network* window. The impairment tooling
exists but is **transport-floor only**:

* `tools/benchmark_weaknet.py` — the portable in-process userspace shaper
  (three tiers: 5% loss / 100 ms jitter / 1 Mbps cap). Cross-platform,
  no root.
* `tools/benchmark_weaknet_netem.sh` — the kernel-side counterpart
  (`tc qdisc netem` inside a throwaway network namespace). Root-only,
  Linux-only.

Both measure the **transport floor** — raw datagrams in, raw datagrams
out. Neither drives the **engine**. The note in the netem script says it
outright: *"transport-floor baseline, not engine glass-to-glass."*

So Q5 is: a **soak that runs the engine under netem**, with reordering
(not just loss — netem's `reorder` is not used by the current script),
and the result archived with its netem parameters, per the v1.2 plan's
DoD: *"soak runs are archived with their netem parameters."*

### 1.6 Q6 (R3) — render clock + A/V sync: **the audio half shipped, the video half did not**

`v1.2.0` closed the audio half of R3.  Audio plan **WP-14** (spec C-4)
makes the engine align **audio playout** against the capture timeline, and
it is switchable.  That work reads the ADR-017 sender-report mapping and
corrects the audio side against it.

The **video** half is untouched:

* there is **no `video_sync` module** — `src/modules/` has no such
  directory, and the renderer seam has no clock;
* `SenderReportTracker` exists and produces the skew, but nothing
  *acts* on it for video: no render clock, no drop / delay decision
  driven by the measured skew;
* the v1.2 plan's Track S work made the skew *visible*.  R3 is the
  **action** half.

That asymmetry is why Q6 belongs in a *quality* release rather than in the
device-layer one the area plan currently files it under.  A caller running
`v1.2.0` gets corrected audio against corrected-nothing video; the longer a
session runs under jitter, the more that difference is the thing the user
notices.  Shipping the audio correction alone is not a partial win — it is
a *new* skew source.

**The two halves must not grow a second skew model.**  The area plan says
this explicitly: both read the same ADR-017 mapping.  Q6 therefore consumes
`SenderReportTracker`'s output; it does not re-derive it.

### 1.7 Q7 (O-6) — hardware encode on the CI matrix: **validated by hand, not by CI**

The hardware codec path has tests, and they run where a GPU exists.  What
the CI matrix does **not** do is exercise an end-to-end hardware encode: the
legs are `windows / msvc`, `linux-gcc / {x86_64,aarch64}`, `macos-clang /
arm64` and the sanitizer legs, none of which is provisioned with an
encoder-capable GPU.

The area plan's Track X already records the consequence and names the
target: *"the CI legs do not all have a hardware encoder; hardware coverage
is validated on a dedicated job or manually, and the software path is what
CI enforces"*, target **`v1.3.0`**.

Q7 is therefore a **coverage** item, not a feature: either a dedicated
self-hosted job with a real GPU, or a recorded, re-runnable manual procedure
with its artifact checked in.  The exit is that the hardware path stops
being the one path nobody re-verifies.

## 2. The sequencing, and why it is this order

The items below are **not** all independent, and the order is the one the
*dependencies* imply — the same rule the v1.2 plan applied to M1.
Q6 and Q7 are ordered separately, after the table.

| Wave | Item | Unblocks | Why here |
|---|---|---|---|
| **1** | **Q2** (bounded memory) | Q5 | A soak that runs for 24 h against a hostile peer is only meaningful if the receiver's memory is bounded first — otherwise the soak measures an out-of-memory kill, not robustness. It is also the **cheapest** item (enforce a config field that already exists) and the one most likely to find a real bug immediately. |
| **2** | **Q4** (receive-side feedback bound) | Q3, Q5 | Q3 removes most of the PLI storms, but not all — the *feedback amplification* half must be bounded for the soak's synthetic-loss profile to be survivable at all. Doing it before Q3 means the two mechanisms are independent and both are measured. |
| **3** | **Q1** (parameter-set switch) | — | Independent of the rest. It is a **test-first** item: the assertion is written, and if it finds a real decoder defect, the fix is local to the codec module. |
| **4** | **Q3** (RTX) | Q4's measurement, Q5 | The heaviest item — a **protocol** change touching the sender's packetizer, the SDP writer, and the receiver's reassembly. Doing it last means the feedback bound (Q4) is already in place to measure its effect, and the memory bound (Q2) is already in place to survive its retransmission cache. |
| **5** | **Q5** (soak under netem) | the M2 exit bar | Last, because a soak is a **measurement of everything above it**. Running it earlier would measure an incomplete build. |

**Q6 and Q7 sit outside this ordering.**  Neither is a prerequisite for
another item and nothing depends on them:

* **Q6** (video render clock) touches the video receive path that Q1 and
  Q2 already touch, so it is sequenced *after* them to avoid two
  concurrent rewrites of the same decode-feed code — but functionally it is
  independent.
* **Q7** (CI coverage) is build and workflow work.  It can start at any
  time, and it should: a hardware-encode job that exists *before* Q6 lands
  gives Q6 a place to prove it on real hardware.

**Q1 is deliberately out of the critical path** — it is independent, so it
can be started in parallel with wave 2, and it is the item most likely to
need iteration (it may find a real decoder defect).

## 3. The items in detail

### Q1 — R2: parameter-set mid-stream switch

**Done when:** a synthetic mid-stream resolution change is decoded
without an error, and **without a key-frame request round-trip**.

**The test** (video plan R2's acceptance, verbatim): *"A synthetic
mid-stream resolution change is decoded without an error."*

**Where it lives:** `src/modules/h264/tests/` (the codec-level assertion)
and `tests/` (the engine-level assertion, alongside
`test_engine_video_e2e_loopback.cpp`, which is the existing proof that a
frame survives the full pipeline).

**The test must fail on the pre-change code.** Two ways it can:

* the *decoder* rejects the frame after the parameter-set change (a real
  defect — OpenH264 needs an explicit flush/re-init, and the vendor
  codec's mid-stream-SPS behaviour is not guaranteed);
* the *engine* drops the frame for a reason that is not the codec's
  fault (a geometry mismatch in the decode buffers, a stale SPS/PPS in
  the pipeline's own state).

If it turns out the mechanism already works, **the test still lands** —
it is the missing evidence, and the v1.2 plan's DoD demands exactly that
("a dedicated test that fails on the pre-change code" applies to the
*behaviour*, and if the behaviour is already right, the honest form of
the test is one that would have caught a regression).

**The H.265 half.** H.265's parameter sets are VPS + SPS + PPS and its
NAL header is two bytes. The tree has an H.265 FU path
(`fu_h265_nalu_type`) but the *decoder* side is a stub. Scope decision:
Q1 covers **H.264** for the assertion; the H.265 parameter-set path is
**recorded as a follow-up** (§6), not silently skipped.

#### Q1 — status: **closed** (2026-11-18)

The mechanism was already right — the survey above said so, and the
assertion confirmed it rather than finding a defect. No production code
changed; what landed is the **evidence**.

**The codec-level half** (`src/modules/h264/tests/test_openh264_software.cpp`):

* `AMidStreamParameterSetSwitchDecodesWithoutAnError` — the *warm*
  decoder case. The decoder first decodes a 320×240 picture (so it is
  holding that SPS / PPS), the encoder's geometry then changes to
  640×480 (`set_params()`), and the new picture is decoded **with the
  same decoder**: no flush, no re-initialisation, no key-frame request.
  The bar is `kOk` on the *first* decode call — a `kErrNotReady` would
  mean the decoder needed another round trip.
* `TheDecodedPictureAfterASwitchCarriesRealSignal` — the geometry-only
  assertion is not enough: a correctly-sized but blank frame would pass
  it, so the decoded luma must carry a real dynamic range.

The two parameter sets are compared byte-for-byte, so the test cannot
pass by decoding the *old* frame twice.

**The engine-level half** (`tests/test_engine_video_e2e_loopback.cpp`):

* `AMidStreamParameterSetSwitchDecodesWithoutAKeyFrameRoundTrip` — the
  full pipeline, with no stub in the middle: two engines, a real
  OpenH264 encoder, real RTP on the wire (STAP-A for the parameter
  sets, FU-A for the slice), the real receiver (depacketize → jitter
  buffer → decode → render into the recording sink). The host pushes a
  320×240 frame, then a 640×480 frame; the receiver must decode both
  and render the *new* geometry.
* The assertion is the plan's own wording: the decode-failure door
  stayed shut (`video_feedback_pli_from_decode_failure == 0`) **and**
  **no PLI datagram went on the wire** — the "no key-frame round-trip"
  half, checked on the wire rather than only in a counter.

**The negative control.** A counter that is *always* zero would satisfy
`== 0` vacuously, so the harness also has to show the counter *does*
move when the decoder really does refuse a frame.
`TheDecodeFailureDoorIsLiveInThisHarness` feeds the receiver a
synthetic single-NAL H.264 picture whose body is nonsense: the
depacketizer accepts it, the jitter buffer assembles it, and the
decoder refuses it — which opens the decode-failure door and moves
the counter. Without that control, the Q1 assertion would prove
nothing.

### Q2 — R4: bounded memory under decode overrun

**Done when:** memory stays bounded under a sustained decode overrun, and
the drop count is reported.

**Status: LANDED (2026-11-18, branch `feat/q2-bounded-jitter-buffer`).**
The enforcement, the byte bound, the seam wiring and the tests are all in
place; the notes below are kept as the *design* record, with the
decisions that were actually taken marked.

**The mechanism.** Two halves, because there are two queues:

1. **The audio jitter buffer** (`src/modules/jb/`) — enforce
   `Config::max_packets`. The declared semantics are already written
   down: *"Hard cap on buffered packets (FIFO trim from oldest when
   exceeded)"*. The enforcement is missing. The trim must count
   `packets_dropped` (the counter exists) and must **not** evict a frame
   that is ready to play out — the video buffer's policy (prefer
   dropping an *incomplete* frame) is the model.
2. **The receiver's decode path** — bound the number of frames handed to
   the decoder between ticks. The engine's receive path drains the
   receiver synchronously in the callback (`drain_frames()` →
   `frame_cb` → decode → render), so an overrun cannot currently queue
   *inside* the engine — but the **jitter buffer** can, and that is where
   the bound belongs.

**The test.** A sustained overrun: push far more packets than the cap
without popping, and assert (a) the buffered count never exceeds the
cap, (b) `packets_dropped` moved, (c) the buffer's *byte* size is
bounded, not just the *packet* count (a packet-count cap alone does not
bound memory when the packets have wildly different sizes — the cap must
account for bytes).

**The public surface.** `Stats` gains the drop counter's *engine-side*
projection. Per D-N6, this is an **additive baseline bump** — the same
PR carries the `scripts/check_api_manifest.py --write` regeneration and
names the symbols it adds. The `docs / markdown links` job then fails if
`docs/api/stats_field_reference.md` is not regenerated to match.

**What actually landed** (the decisions the design record above left
open):

* **The byte bound is a new config field.** `jb::Config::max_bytes`
  (default 4 MiB) joins `max_packets` (default 512). Both are enforced
  in the same loop, so the buffer is inside *both* of them once the
  insert is done. `0` disables either half.
* **The trim runs *before* the insert**, so the packet that has just
  arrived can never be the one the bound evicts. This is the video
  buffer's `enforce_inflight_cap(incoming=1)` rule applied verbatim —
  without it, the newest audio would always be the first to be dropped.
* **The victim is the oldest frame** (the map is keyed by RTP timestamp),
  which is the frame that has already missed its slot. The audio buffer
  has no frame *assembly*, so the video buffer's "prefer the incomplete
  frame" rule has no analogue here; the FIFO-from-the-oldest rule is
  what `Config::max_packets` always declared.
* **The seam carries the cap.** `plugins::JBConfig` gains
  `max_packets` (`0` = "use the implementation's default", negative =
  unbounded), so a host can reach the bound without touching the
  concrete module.
* **The drop counter is reported all the way up**:
  `jb::Stats::packets_dropped` → `plugins::IJB::Stats::packets_dropped`
  → `plugins::IAudioReceiver::Stats::packets_dropped` →
  `Engine::Stats::audio_packets_dropped` and
  `AudioStreamStats::packets_dropped`.
* **The tests** (all of which fail on the pre-change code):
  `src/modules/jb/tests/test_jb.cpp` (the bound itself — 9 cases),
  `src/modules/jb/tests/test_jb_plugin.cpp` (the seam — 5 cases), and a
  propagation case in `src/modules/audio_rx/tests/test_audio_rx.cpp`.

### Q3 — T1: RTX (RFC 4588)

**Done when:** a NACK for a lost packet is answered by an RTX packet on
the RTX payload type, and the receiver restores the original sequence
number.

**The mechanism**, in the order the pieces have to exist:

1. **The payload type.** The SDP writer emits the RTX payload type with
   `a=rtpmap:<pt> rtx/90000` and `a=fmtp:<pt> apt=<original-pt>`. The
   `apt=` parameter is the *association* — it is how the receiver knows
   which stream the retransmission belongs to. Both the video payload
   module and the SDP module already know how to write `rtpmap` /
   `fmtp` lines.
2. **The packet format.** RFC 4588 §4.1: the RTX payload is the
   **two-byte** original sequence number (OSN, in network byte order),
   followed by the original payload — and **nothing else**.  The header
   is exactly two octets; there is no marker byte in front of it.  (The
   `0x90` marker some descriptions of RTX mention is not in RFC 4588,
   and a peer that sent one would have its sequence number restored
   `0x9000` too large.)
3. **The sender.** The retransmission ring already holds the original
   packet's payload and sequence number — it needs to also remember the
   *payload type* the original was sent under, and to build the RTX
   header when it answers a NACK. The ring's size is already bounded
   (`retransmit_cache_packets`), so the RTX path adds **no unbounded
   memory**.
4. **The receiver.** The RTX packet arrives with **its own** sequence
   number on the **RTX** payload type. The receiver must (a) recognise
   the payload type, (b) unwrap the header, (c) restore the original
   sequence number, (d) splice the payload into the frame it belongs to.
   Point (d) is the delicate one: the receiver's reassembly is keyed on
   the sequence number, so the restored number must be used *everywhere*
   the original would have been — including the NACK bookkeeping, or
   the receiver will NACK the same packet again.

**The receiver's frame assembly is where the RTX payload has to land.**
This is the part most likely to be got wrong, and the test must pin it:
*"the receiver restores the original sequence number"* is the acceptance,
and "the restored packet lands in the **right frame**" is the thing that
proves it.

**The scope boundary.** RTX is negotiated, so it is **optional**. A peer
that does not offer an RTX payload type must keep working exactly as it
does today. The test suite needs both shapes: with RTX negotiated, and
without.

#### Q3 — status: **closed** (2026-11-18)

The retransmission stream now exists end to end: the SDP advertises it,
the sender frames it, the wire carries it, and the receiver unwraps it.

| Piece | Where it lives |
|---|---|
| The wire format (the two-octet OSN header, the `apt=` / `rtx-time=` parameters) | `src/modules/rtx/` — a standalone format module, header-only API over `nimrtc::core` |
| The plugin seams | `plugins::IVideoSender` (`rtx_payload_type`, `set_rtx_enabled()`, `set_rtx_packet_callback()`) and `plugins::IVideoReceiver` (`rtx_payload_type`, `set_rtx_payload_type()`, `push_rtp_rtx()`) — all additive, with defaults that keep a non-RTX plugin working unchanged |
| The sender | `src/modules/video_pipeline/` — the retransmission cache builds the OSN header, the RTX stream keeps its **own** sequence-number space (RFC 4588 §4), and the counter reaches `Stats` as `rtx_packets_emitted` |
| The receiver | `src/modules/video_pipeline/` — the OSN header is unwrapped, the **original** sequence number is restored, and the packet is spliced into the frame it belongs to (and erased from the pending-NACK list, or the receiver would ask for it again) |
| The SDP | `src/engine/src/engine_signaling.cpp` + `video_rtx_negotiation.hpp` — `a=rtpmap:<pt> rtx/90000`, `a=fmtp:<pt> apt=<vpt>`, and `a=ssrc-group:FID <media_ssrc> <rtx_ssrc>` with its own `a=ssrc:` line (RFC 5576 §4.2) |
| The wire | `src/engine/src/engine_media.cpp` / `engine_timeline.cpp` — the outbound path stamps the RTX payload type, the RTX SSRC and the RTX sequence number; the inbound path demuxes on the payload type and routes to the unwrapper |

**Three decisions the RFCs forced**, each of which is a place a
plausible-looking implementation gets it wrong:

* **The header is two octets, not three.** RFC 4588 §4.1 defines no
  marker byte; the `0x90` this plan originally described is not in the
  RFC, and a peer that sent one would have its sequence number restored
  `0x9000` too large. (The plan's §3 text was corrected.)
* **The FID group lists the media SSRC first.** RFC 5576 §4.2's FID
  semantics relate a *primary* source to its *dependent* ones, and the
  primary comes first — `a=ssrc-group:FID <media_ssrc> <rtx_ssrc>`.
  The reverse order is a real interop hazard: a receiver that follows
  the convention would treat the media stream as the repair flow and
  drop the picture.
* **One payload type serves both directions.** RFC 8843 (Unified Plan)
  gives an m-section a *single* payload-type list, so the RTX payload
  type is a property of the m-section, not of a direction — which is
  also how Chrome negotiates it. The `apt=` parameter then says which
  payload type *within* the section the retransmission protects.

**The scope boundary holds.** A peer that offers no RTX payload type
gets no RTX stream, and the sender falls back to re-sending the original
packet (the pre-RTX behaviour). Both shapes are pinned by the tests.

**The tests** are in three places, and each covers a different layer:
`src/modules/rtx/tests/` (the format), `src/modules/video_pipeline/tests/test_video_pipeline_rtx.cpp`
(the mechanism), and `tests/test_engine_video_rtx.cpp` (the negotiation
and the wire — the two halves only the engine can do).

### Q4 — T2: PLI/FIR rate limiting (the receive side)

**Done when:** no IDR storm under a sustained loss profile, asserted over
a **30 s synthetic-loss run**; and the receiver's feedback volume is
bounded.

**What is already there** (§1.4): the sender's `KeyframeLimiter`, the
engine's 250 ms receive-side throttle, the per-type feedback counters.

**What is missing:**

1. **The receiver's PLI emission is not counted separately from the
   engine's decode-failure throttle.** A receiver that detects loss in
   the jitter buffer (`request_keyframe()`) and a receiver whose decoder
   refuses a frame (`request_keyframe_on_decode_failure()`) are two
   different doors into the *same* pending report — and the pending
   report is **merged**, so the two cannot be told apart in the stats.
   The fix: count each door, and expose the counts.
2. **The receiver's NACK emission is uncapped.** `pending_nacks` grows
   with every detected gap. A peer that drops 30% of a 30 fps stream
   produces a NACK list that grows without bound, and the merged RTCP
   report grows with it. The fix: a **cap** on the NACKs per report (the
   RFC 4585 §6.2.1 shape: the receiver NACKs the most recent losses
   first, not the whole history).
3. **The pending feedback report has no age.** A report that sits in the
   queue while the link is down is stale by the time it goes out.

**The 30 s synthetic-loss run** is the acceptance. It is a *test*, not a
soak — it runs in CI, on every PR, and it is deterministic (the loss
profile is generated, not induced by a real network). Q5 is the
*uncontrolled* version of the same measurement.

#### Q4 — status: **closed** (2026-11-18)

The three gaps above are closed by one private collaborator,
`src/engine/src/engine_feedback_guard.{hpp,cpp}` (`detail::FeedbackGuard`),
which owns the bound and the per-door counting in a single place.

| Gap | How it is closed |
|---|---|
| The two doors are indistinguishable | `FeedbackSource::kLoss` / `kDecodeFailure` — the engine's loss door (`queue_video_feedback()`) and its decode-failure door (`queue_video_feedback_from_decode_failure()`) are counted separately, and the counts reach `Stats` as `video_feedback_pli_from_loss` / `video_feedback_pli_from_decode_failure` |
| The NACK list is uncapped | `Config::max_nack_seqs` (default 64) bounds the **pending report**; the overflow drops the *oldest* candidates (RFC 4585 §6.2.1 shapes the request around the recent losses) and counts the drops as `video_feedback_nack_seqs_dropped` |
| The pending report has no age | `Config::max_report_age_us` (default 1 s) drops a report that sat in the queue too long; the drops count as `video_feedback_reports_expired` |

The **key-frame rate limit is global** (`Config::min_pli_interval_us`,
default 250 ms = 4 Hz, RFC 5104 §4.3.1.1) — not per-door, because the
peer's encoder is the shared resource the limit protects. The engine's
own decode-failure throttle stays as the *door's* throttle (it keeps the
log quiet); the guard holds the limit that covers both doors.

The guard's clock is **injected**, which is what makes the acceptance
deterministic: the engine passes the monotonic clock, the test passes a
virtual one it advances by hand. `tests/test_engine_feedback_guard.cpp`
therefore runs the 30 s synthetic-loss profile in microseconds of real
time and asserts the same numbers on every machine.

The acceptance, as pinned by the test:

* a 30 s run at 30 fps with 30 % loss raises ~270 key-frame requests and
  lets **at most 121** through (30 s / 250 ms + 1);
* the adversarial variant — a link that loses **everything**, 901
  requests — still lets at most 121 through;
* every request is accounted for (`allowed + suppressed == requested`);
* every report that goes out carries at most 64 NACK sequence numbers.

The engine-level half (that the doors reach the guard, that the guard's
counters reach `Stats`, and that the bounds are configurable through
`EngineConfig`) is in `tests/test_engine_video_feedback.cpp`.

### Q5 — long soak across NAT + netem

**Done when:** a 24 h+ run completes green under reordering + loss +
jitter, and the run is **archived with its netem parameters**.

**The gap** (§1.5): the existing soak tooling measures a *clean* network
and the *transport floor*; the impairment tooling does not drive the
engine.

**What has to be built:**

1. **An engine-level impairment harness.** The existing
   `tools/benchmark_weaknet_netem.sh` runs inside a throwaway network
   namespace with `tc qdisc netem` on `lo`. The engine-level version
   runs the **engine** (the same `demo-p2p` loopback the acceptance
   runner drives) inside that namespace, so the impairments hit the
   *real* RTP path.
2. **`reorder` must be added.** The current script's tiers are
   `loss`, `delay+jitter`, `rate`. Netem's `reorder` is not used at all,
   and the v1.2 plan's Q5 row explicitly names **reordering** as one of
   the three impairments.
3. **The NAT leg.** "across NAT" is in Q5's wording. The engine already
   has a TURN transport, but Track C's C1 (real TURN/TLS) is **not**
   landed — so the NAT leg has to be honest about what it exercises. Two
   options, and this is an owner decision (§5): a **local TURN server**
   under `examples/` (which is C5's job, scheduled for M3) or a
   **simulated** NAT (an address-translating relay that is not a TURN
   server). The v1.3 plan's default is the **simulated** NAT, so Q5 does
   not depend on Track C; the *real* TURN leg is explicitly deferred to
   v1.4.0 and recorded in the evidence.
4. **The archive.** The netem parameters travel with the result:
   `loss`, `delay`, `jitter`, `reorder`, `rate`, the duration, the tree
   it was measured on, and the engine version — the same fields the
   existing soak collector already carries (`git_ref`, `git_commit`,
   `git_dirty`). The v1.2 plan's DoD is explicit: *"soak runs are
   archived with their netem parameters."*

**What "green" means.** The soak is a **measurement**, and a measurement
that fails must be able to say *what* it measured. The invariant set is
the one the E6 benchmark already uses (a saturated link, a reached rate,
a p99 inside a budget, no loss, different 5-tuples) — applied to the
24 h run, plus the Q2 bound (memory did not grow) and the Q4 bound (the
feedback rate did not grow).

### Q6 — R3: render clock + A/V sync (the video half)

**Done when:** an A/V skew that exceeds the configured tolerance produces
a **documented drop or delay correction** on the video side, asserted in a
test with a synthetic skew; and **no second skew model** exists.

**The gap** (§1.6): the audio half shipped in `v1.2.0`; the video half has
no module and no action.  `SenderReportTracker` produces the skew, and
nothing consumes it for video.

**What has to be built:**

1. **A `video_sync` module** (`src/modules/video_sync/`, per L3), holding
   the render clock and the correction policy.  It is a *module*, not a
   field in the engine: the engine's job is to wire it (L4), and the
   policy must be testable without a live session.
2. **The correction decision, driven by the measured skew.**  The policy
   is the same shape the audio side uses — but the *actions* differ,
   because video cannot stretch: a video frame is either rendered at the
   clock's instant, or dropped, or re-ordered.  The module decides
   *which*, from the measured skew and the jitter buffer's current
   occupancy.
3. **The seam.**  The renderer already has a display path; what it lacks
   is a **clock it renders against**.  The seam is additive: the
   renderer is told the presentation instant, it does not derive it.
4. **The test.**  A synthetic skew (the sender-report mapping is fed a
   known offset) must produce a deterministic correction — the same
   discipline Q1 and Q4 use: a test that fails on the pre-change code.

**What it must not do.**  It must not grow a second skew model.  Both
halves read the ADR-017 mapping; if Q6 finds the mapping insufficient, the
mapping is amended, not duplicated.  That constraint is inherited verbatim
from the area plan (§R3's scope note), and it is the one most likely to be
violated by accident — a render clock that keeps its own "capture time"
accumulator *is* a second model.

**Public surface.**  Q6 adds no `Config` field and no `Stats` field that
the Track S surface did not already carry: the skew is *visible* already,
so the correction's effect is measured against the observable that
exists.  If a correction counter is warranted, it is additive and carries
the manifest regeneration, per D-N6.

### Q7 — O-6: end-to-end hardware encode on the CI matrix

**Done when:** the hardware codec path is exercised **end-to-end** by
something that re-runs without a human remembering to, and its result is
visible on a run that the PR gate can point at.

**The gap** (§1.7): the CI legs have no encoder-capable GPU; the hardware
path is validated by hand.

**Two shapes, and the choice is the owner's (§5):**

* **A dedicated self-hosted job.**  The existing `soak.yml` already runs
  on a self-hosted machine and already has the artifact machinery; a
  hardware-encode job on the same class of runner is the same pattern.
  This is the shape that actually gates.
* **A recorded manual procedure with a checked-in artifact.**  Cheaper,
  and it is honest about being manual — but a procedure that nobody
  re-runs is a procedure that has already failed silently at least once.
  If this shape is chosen, the recorded artifact must carry a date and a
  driver-version stamp, and the plan's evidence says so.

**What "end-to-end" means.**  Not "the module's unit tests ran with a GPU
present".  The claim is *"a frame was captured, encoded by the hardware
codec, transmitted, decoded, and rendered, and the pipeline reported
hardware encoding"* — asserted from the stats, not from a log line.

**Why it is in a quality release.**  It is not, strictly — it is
*coverage*.  It is here because O-6's target is `v1.3.0`, and because the
resilience claims Q1–Q6 make are *stronger* if the hardware path is known
to still work after the receive-side changes Q1/Q2/Q6 touch.

  decoder to assert on.

  does exist — Q5's NAT leg — is handled by Q5-1's simulated-NAT default
  and recorded as a known evidence gap.
* **HEVC software decode** and **H.264/H.265 simulcast**.
* **A rewrite of the RTP/SDP contract layer** — ADR-025 stands. Q3
  (RTX) adds a payload type and an SDP line; it does **not** touch the
  RTP/SDP contract.
