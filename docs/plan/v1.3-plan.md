## 1. Goal

v1.0 交付了"能打通"，v1.1/v1.2 交付了"可验证、可打包"。**v1.3 交付"弱网下体验可用"+ "差异化能力进公共 API"**。

具体三件事：

1. 把质量链路从"能通话"推到"弱网下不崩、控制不丢"（自适应 JB + 反馈闭环 + 完整 BWE + 弱网基线）。
2. 把 NimRTC 真正差异化的两块（`ref_frame` 时间线对齐、命令-画面关联）从模块内部提到 engine 公共 API。
3. 让视频统计成为引擎级可观测面，并把**对外口径**修准（Profile 组合边界 + 国密覆盖范围）。

**场景优先级（2026-11-04 BDFL 决策）**：主力押 **AI Agent**（`agent` / `agent-gateway` / `agent-low-latency` / `relay-agent`）+ **具身智能遥操作**（`teleop` 同族复用，不新增 Profile）。`cloudgame` 不进官方组合、顺延 v1.4+；`takeover`（远程驾驶接管）归 P4。理由见 Track V 的 V2 决策记录。

不做：新协议（SFrame / MLS / DTLS 1.3 强制）、SFU 复活（§7 = NO）、生产部署保证、`cloudgame` 官方 Profile。

> **V2 决策记录（2026-11-04，BDFL）**：`cloudgame` **不进 v1.3 官方 Profile 组合**，顺延至 v1.4+。
> 理由：(a) cloudgame 相对 `teleop` 的 4 处覆盖中，最硬的一条"输入↔渲染帧对齐"依赖**渲染端**（Unreal / Unity 等）提供渲染帧时间戳，超出引擎能力边界——引擎不捆绑编解码器（§13 codec 行），GPU 硬编接入与渲染管线接入亦不在本项目范围；
> (b) 云游戏的竞争维度是端到端延迟指标 + GPU 编解码管线，NimRTC 难以在此形成可证差异化；
> (c) 其余 3 处覆盖（BWE 高码率主线 / 帧级 timeline / 输入严格优先级）均已被 `teleop` 族 + T1/T2 覆盖，边际增量价值低；
> (d) Profile 本身成本极低（JSON + 常量 + 字节级回归），若只为"进官方组合"而做，是**低价值承诺**。
> 结论：**优先押 AI Agent（`agent` / `agent-gateway` / `agent-low-latency` / `relay-agent`）与具身智能遥操作（`teleop` 同族复用）**——这两类场景的差异化（PCM tap 原语、严格优先级 DC、ref_frame 时间线）已在引擎能力边界内且已有实现基础。远程驾驶接管（`takeover`）归 P4（双链路 + dead-man），v1.3 不做。

### Track X — 国密 / 平台（3 项，本版仅做可验证部分）

| ID | Item | Acceptance |
|---|---|---|
| X1 | **GMSSL 作为 submodule 进 `src/third_party/gmssl`**（决策：submodule + 默认 OFF 编译 + CI opt-in 腿） | ① **vendoring 前置**：核对 pinned commit 的 GmSSL LICENSE 原文并写入 `vendor.json`（`license` 字段），确认与 Apache-2.0 兼容；② `src/third_party/gmssl` 作为 git submodule 引入（pin commit，`.gitmodules` + `vendor.json` 同步）；③ `NIMRTC_ENABLE_DTLS_GMSSL=ON` 时改走 `add_subdirectory`，**不再需要 `find_path`/`find_library` 探测系统安装**；④ 默认仍为 OFF（默认构建产物 / 体积 / 耗时不变，非国密用户零成本）；⑤ CI 增加一条 opt-in 腿实证；⑥ **新增 Windows/MSVC 编译验收项**（GMSSL v3 在 MSVC 上坑较多，"vendored 后开箱即用"在 Windows 上成立与否取决于此） |
| X2 | **SRTP 后端 seam（只落 seam，不实现 SM4-GCM）** | `src/plugins/` 增加 SRTP 后端抽象 seam（`ISrtpBackend` / 工厂接口，non-breaking additive）；`src/modules/srtp/` 现有 libsrtp 实现改为经由 seam 接入；**SM4-GCM SRTP 实现明确推到 v1.4+**（工作量与 D1「安全关键件不自研」约束见下方决策记录）；本版不产出 SM4-GCM 加密流量 |
| X3 | **OHOS Stage 1 续**：OH-DOD-1/2/3 在有 SDK 的机器上实证 | `debug.ohos-arm64` 零 error；`libnimrtc_engine.a` 零未解符号；`test_dtls_gcm_aead` 在 OHOS PASS |

> **X1 决策记录（2026-11-04，BDFL）**：GMSSL 采用 **submodule + 默认 OFF 编译 + CI opt-in 腿**。
> 理由：(a) OHOS / aarch64 交叉编译场景下"系统安装 GMSSL"实际不可行——ADR-013 的动机正是此，而要求每个下游自行编译并安装到 sysroot 等于把集成门槛原样还回去；(b) 仓库已有 wolfSSL / msquic / libsrtp / libopus 的 submodule 先例，GMSSL 是唯一例外，这种不一致本身即摩擦；(c) ADR-013 决策第 6 条称"与 wolfSSL 保持一致（wolfSSL 也未 vendoring）"，该前提**已过时**——wolfSSL 实际已 vendored 成 submodule，故本次是**修正过时陈述**，不是推翻原决策。
> 约束：(a) vendoring 前必须核对 GmSSL v3 LICENSE 原文并写入 `vendor.json`（合规动作，非形式）；(b) 保持默认 OFF，避免给非国密用户增加构建时间与产物体积；(c) X1 验收须含 Windows/MSVC 编译 + `test_dtls_gmssl_tlcp` PASS。

> **X2 决策记录（2026-11-04，BDFL）**：本版**只落 SRTP 后端 seam，SM4-GCM SRTP 实现推到 v1.4+**。
> 理由：(a) libsrtp 不支持 SM4，SM4-GCM SRTP 需自行实现 RFC 3711 的 KDF 派生（PRF 换 SM3）、keystream 与认证 tag，并保证与对端逐字节一致——这是真正的密码学实现，工作量被低估；(b) 违反 D1「安全关键件不自研」：涉媒体加密的自研实现一旦宣称即招安全审计压力，合理路径是寻找现成实现或外部贡献。
> **可实用性判据（供对外口径引用）**：国密合规分三层——信令链路国密 TLS（TLCP，GB/T 38636 / RFC 8998）**不属于引擎范围**（§10 表格已明确"上层"）；DTLS 国密套件（TLCP + SM2/SM3/SM4）**在引擎内**，由 X1 覆盖；SRTP SM4-GCM **在引擎内但本版不做**。因此多数非涉密政企项目在 X1 交付后即可落地（媒体流走国际套件通常不被卡），而"端到端必须国密"的关基 / 部分车联网项目须等 X2 的后续版本。
> **强制配套动作**：README 的"GM/T cryptography ready"表述必须同步收敛为"**DTLS/TLCP 已覆盖，SRTP 仍为国际套件**"——否则对政企客户构成合规误述。

## 4. Sequencing

```
前置: v1.2 P 轨闭环（Linux 下游证明 + Linux bench 首绿 + W3/W5 翻转 + CHANGELOG 1.1.0）

线 A（质量）: Q2 → Q3 → Q1        （JB 统一是反馈闭环的前置）
线 B（时间线）: T1 → T2            （T2 依赖 T1 的帧映射）
线 C（观测）  : V1 ‖ V2            （V2 = 文档口径修正，无代码冲突，可最早做）
线 D（国密/平台）: X1 → X2 ；X3 独立（不挡 A–C）
线 E（工程债）: R1 与 A/B/C 无文件冲突，可并行
```

- 每 PR ≤ 400 LOC；公共头改动只 additive + `NIMRTC_API_UNSTABLE`。
- 每 PR 必跑相关 `ctest` 子集 + `scripts/check-release-freeze.sh`。
- Q1 的 BWE 默认值保持 AIMD（不改默认行为），切换需显式 opt-in。

| Risk | Mitigation |
|---|---|

## 7. 明确不做 / 已决策

**不做（本版）**：SFU-1 / DC-3 / BENCH-1 复活（`v1.0-plan.md` §7 = NO，2026-10-19 BDFL 决策）；SFrame / MLS / DTLS 1.3 强制；双链路 / 接管方案（§8.5 归 P4）；生产部署保证；**`cloudgame` 官方 Profile**（顺延 v1.4+）；**SM4-GCM SRTP 实现**（v1.3 只落 seam）。

**已决策（2026-11-04，BDFL）**——原 §7 三项待决全部关闭：

1. **`cloudgame` Profile 是否进入官方组合** → **否**。不进 v1.3 官方组合，顺延 v1.4+；本版只做文档口径修正（V2）。理由：其最硬的覆盖项"输入↔渲染帧对齐"依赖渲染端提供渲染帧时间戳，超出引擎边界；竞争维度（GPU 编解码 + 端到端延迟指标）不构成可证差异化；其余覆盖已被 `teleop` 族 + T1/T2 覆盖。
2. **GMSSL 依赖形态** → **submodule 进 `src/third_party/gmssl`**，默认 OFF 编译 + CI opt-in 腿 + Windows/MSVC 编译验收项；vendoring 前须核对 LICENSE 原文写入 `vendor.json`。ADR-013 决策 6 的"wolfSSL 未 vendoring"前提已过时，需同步修正（见 X1 决策记录）。
3. **国密 SRTP 后端本版做到哪一步** → **只落 SRTP 后端 seam**，SM4-GCM SRTP 实现推到 v1.4+（工作量 + D1「安全关键件不自研」双重约束）。配套必须修正 README 的国密口径为"DTLS/TLCP 已覆盖，SRTP 仍为国际套件"。

**场景优先级（同期决策）**：主力 = **AI Agent**（4 个 Profile 已在注册表）+ **具身智能遥操作**（`teleop` 同族复用）；`takeover` 归 P4；`cloudgame` 顺延。
