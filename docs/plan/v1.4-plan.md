## 0. The product claim this release has to make true

> **A host application gets a working call from a few lines of code.**

That sentence is the acceptance criterion for the whole release.  It is
not true today, and the survey in §1 shows exactly why — not because any
single piece is missing, but because **every piece exists and none of them
is joined to the engine**:

> **Update 2026-11-27: eight of the sixteen items are closed, and the
> gap is now entirely the joins.**  N1 (real TURN/TLS), N5 (the
> reference TURN deployment), D2 (the engine runs the renderer), D1
> (the engine runs the audio device layer), N4 (connectivity
> diagnostics), D6 (the connectivity profile), D3 (the default device
> policy) and D4 (camera hot-plug) have landed since §1 was written;
> §0a says what each of them is now, and the survey's stale rows are
> marked in place.  Eight remain, and **not one of them is a missing
> module** — each is either the engine reaching a seam that already
> exists (D5, D7) or the host being told something the engine already
> knows (N3, N7, N8) or the remaining mechanisms (N2, N6, N9).  The
> release's thesis has not changed; it has narrowed.  The verification
> table in §10 is now **executed** by `tools/check_v14_plan_status.py`,
> so the next drift is reported rather than discovered.

* **Network side.**  TURN/TLS is accepted and silently degraded to plain
  TCP; ICE has no TCP candidates; a network change needs the host to call
  `restart_ice()` by hand; a session that never connects says only
  `"failed"`.  A host that ships today must write its own connectivity
  policy — which is the definition of "not an SDK".
* **Device side.**  **Update 2026-11-27: D1, D2, D3 and D4 are closed — the
  engine now consumes the audio device layer and the video sink, owns the
  default device policy, and watches the capture device list.**  It was: the
  audio and video device layers exist as
  *modules* and as *seams*, but the **engine consumes neither**: there is
  no `IAudioSource` / `IAudioSink` in `src/engine/` at all, and the video
  capture path is wired while the **audio device path, the renderer and
  the camera are the host’s job**.  The remote-desktop example carries
  ~100 KB of C++/Python to stand in for what the SDK should provide.
  What is **still** the host’s job: the DTX / concealment coupling (D5)
  and the call-state callback (D7).
* **API side.**  There is no one-call lifecycle, no call-level state
  machine (the raw ICE state string and the raw control bytes exist, but
  nothing joins them into "the call is up / reconnecting / failed and
  why"), no connectivity profile that turns traversal on by default, and
  the credential / path-change / packaging seams a real deployment needs
  are the host's to invent.

v1.4.0's theme is therefore **adaptation, in both directions**:

| Axis | What "adapted" means | Exit |
|---|---|---|
| **Network** | the session finds a path through whatever the network allows (UDP, TCP, TLS-only, relay), survives the path changing, and says why when it cannot | two peers behind a TLS-only NAT carry a call; the path is named in the stats |
| **Device** | the session uses whatever camera / microphone / speaker / display the machine has, opens without the host enumerating anything, and recovers when it changes | the same binary runs on Windows / macOS / Linux with **no device ids configured** |
| **API** | the host writes an application, not a pipeline | the "few lines" sample compiles and runs in CI's acceptance leg |

### 1.3 API — what "a few lines" costs today

> **Update 2026-11-27: the connectivity-policy half of this row has
> changed** (D6 is closed).  It is kept below as the snapshot §1 was
> written against, with the stale claim marked in place.

The loopback example `examples/loopback-p2p` and `examples/demo-p2p` are
the closest to a minimal application, and the remote-desktop pair
(`rd_device.cpp` 33 KB + `rd_viewer.cpp` 30 KB + `rd_signalling.hpp` +
`rd_signalling.py` 41 KB + `client.py` 31 KB) is what a real application
costs today.  The signalling server is a product concern (RD-7), but
**the device policy, the connectivity policy and the render path are not**
— they are the SDK's job, and they are the host's today.

Concretely, a host today has to write, before its first frame or sample
exists: a per-platform device-default table (it lives in `rd_device.cpp`),
a renderer and its present loop (it lives in `rd_viewer.cpp`), a
connectivity policy (STUN/TURN list, when to relay, when to restart) —
**the last one is now the engine's** (D6: `EngineConfig::connectivity_profile`
names a policy and the host's explicit keys still win) —, a
credential lifecycle (`pre_open()` → `add_turn_server()` → `open()`, plus
its own refresh), and a state machine over `ice_state_string()` and
`Stats` to answer "is the call up, and if not why".  None of those is the
application's product; all of them are the host's code today.

whose next reader does the wrong work.

> STALE.**  When N4 and D6 landed, their rows were flipped from

> keeps asserting the absence of a thing that now exists reports
> STALE forever — a permanent false alarm, which is how a checker
> teaches people to ignore it.

> "there is no connectivity profile", but that is **D6's** claim, not

## 3. Track N — network adaptation

### N5 — reference TURN deployment under `examples/turn-server/`

**Done when:** one command brings up a TURN server that CI's network
tests point at, with a `--require-tls` mode that **refuses plain TCP**, so
a TURN/TLS test cannot pass by falling back.

**The shape.**  §5 **N5-1**: the *developer* path is a local container (coturn is the reference
implementation; it stays out of `src/third_party/` and out of the
installed library — this is a *deployment*, not a vendored dependency).
The directory carries the compose file, the server config (long-term
credentials, the TLS material generator, the require-TLS switch), and a
README that is the deployment document.

**How CI uses it without Docker.**  The N1 / N2 tests run on GitHub's
hosted runners, and the reference deployment is a container image that
needs a daemon.  §5 **N5-2** decides the CI shape; the default is **a
native `coturn` install on the Linux leg** (`apt-get install coturn`, a
generated self-signed cert, `--tls-only`), with the compose file serving
the *developer* and *archived-evidence* paths in `examples/turn-server/`.
The test itself only knows "a TURN URI and a credential" — it does not
care which path brought the server up, which is what keeps the claim
honest on both.

> **Update 2026-11-20: the deployment exists; its "done when" is still
> one gate short, and so is its *silence*.**
>
> The directory is written (`compose`, `turnserver.conf`, `gen-certs.sh`,
> the README), and it was reviewed against coturn's own source rather
> than against its documentation.  That review found **seven defects,
> every one of them silent** — coturn's answer to a misconfigured
> deployment is to *start anyway*, so the container comes up healthy,
> the port is published, and the property the deployment exists to
> establish (a client told "use TLS" cannot fall back to plain TCP) is
> false.  The two that mattered most:
>
> * a second `--tls-listening-port=443` in the compose file.  coturn
>   parses the config file first and the command line second, and the
>   command line **replaces** the value rather than adding a listener —
>   so the TLS listener moved off 5349 and that port fell back to plain
>   TCP.  The deployment meant to catch exactly that defect was
>   producing it.
> * the private key was left at OpenSSL's 0600, and the coturn image
>   runs as `nobody`.  An unreadable key is coturn's cue to disable the
>   TLS listener and carry on.
>
> The fix is not only the seven edits: `tools/check_turn_server.py`
> pins them, and its own self-test re-introduces each defect into a
> scratch copy of the tree and requires the check to fail — because a
> guard that cannot fail is not a guard.
>
> **What is still open.**  N5's "done when" asks for "one command"
> **and** "a CI job that starts it" (§6).  The deployment is one
> command; the CI job is **N5-2**, and it is not written.  So N5 is
> *not* closed — it is written, reviewed and guarded, with the CI leg
> still owed.
>
> ---
>
> **Update 2026-11-20 (later): the CI leg is written, and writing it
> found three more defects.**
>
> The static guard (`tools/check_turn_server.py`) was not enough, and
> the reason is structural: it checks the *files* against coturn's
> option vocabulary, but **coturn's answer to a misconfigured
> deployment is to start anyway**.  A missing config file, a TLS
> listener on the wrong port, an unreadable key — each leaves a
> healthy server behind that answers with something that is not TLS.
> So the CI leg has to assert the *behaviour*, not the spelling.
>
> The leg is `linux-turn / reference TURN server`: a native `coturn`
> on the Linux runner (the hosted runners have no Docker daemon), and
> it asserts a TLS handshake that verifies against the generated CA, a
> **real TURN allocation** over that TLS session (with coturn's own
> `turnutils_uclient`), the server log's `cipher=… method=TLSv1.2`
> line, and — the negative control — that **the same client, on the
> same port**, against a plain TURN server, gets *no* allocation.
>
> Writing it found three more defects, each of which is silent in the
> same way:
>
> * **`--config` is not a coturn option.**  The option is `-c`.
>   `--config=…` makes the server print "unrecognized option" and
>   **exit** — so the container never started, and the failure read
>   like a Docker problem rather than a spelling problem.
> * **The configuration file was never mounted.**  It lives in the
>   directory, not in `secrets/` (which is gitignored, because it
>   holds the generated key material), so mounting `./secrets` alone
>   left `/etc/coturn/turnserver.conf` absent.  coturn's response to a
>   missing config file is "Default and command-line settings will be
>   used" — so the server started with **no realm, no user, no
>   certificate, and therefore no TLS listener**.
> * **A command-line `--log-file` is silently ignored.**  coturn's
>   `set_option()` lists `'l'` among the options "already taken care
>   of before", and the pass that applies the config file's `log-file=`
>   runs *after* the command line.  The compose file separated the
>   two runs' logs that way, so both runs would have written to the
>   *same* file and the control's run would have destroyed the
>   positive server's evidence.  The control now has its own
>   configuration file (`turnserver.plain.conf`).
>
> The three are now guarded too, and the guard's self-test has grown
> from seven mutation cases to twelve.
>
> **What is still open.**  N5's "done when" also asks for a
> `--require-tls` mode that **refuses plain TCP**.  What the
> deployment actually does is refuse plain TCP *on the TLS port* — the
> plain listener is on 3478 and the TLS listener on 5349, and the
> negative control takes 5349 with TLS off.  There is no coturn
> `--tls-only` option, so "the TLS port speaks only TLS" is what the
> deployment's shape gives, and the leg asserts it.

### N4 — connectivity diagnostics

**Done when:** a session that never connects says **why** from the stats
snapshot alone.

**The mechanism.**  Additive fields on `Stats::transport` (D-N6: the PR
carries the `scripts/check_api_manifest.py --write` regeneration and names
the symbols):

* `ice_gathering_state` (`"new"` / `"gathering"` / `"complete"`) and the
  candidate count per type (`host` / `srflx` / `relay`) — so "no relay
  candidate" is answerable;
* `ice_failure_reason` — a small closed vocabulary (`"none"`,
  `"no-candidates"`, `"no-pair"`, `"checks-failed"`,
  `"credentials-rejected"`, `"transport-unsupported"`);
* `turn_transport_used` (`"udp"` / `"tcp"` / `"tls"`) — the field that
  would have caught the silent plain-TCP fallback, and N1's own
  observable.

§5 **N4-1** decides whether a discarded-candidate-pair list is in scope;
the default is **no** (libjuice sees only the nominated pair; an
engine-maintained list would describe the engine, not the network).

> **2026-11-27 update: N4 is landed.**  All six fields are on
> `TransportStats`, and the vocabulary is closed at the six values above.
>
> **Two things the original text left open, and how they were decided.**
>
> * **The failure priority.**  The order is
>   `transport-unsupported` → `credentials-rejected` → `no-candidates` →
>   `checks-failed` → `no-pair` → `none`.  The last two are the pair the
>   original text left in the other order, and the reason is that a
>   session whose agent has already **given up** has candidates *and* no
>   nominated pair — both facts are true — but `"no-pair"` reads as
>   "still waiting for one", and a session that gave up is not waiting.
>   So `"no-pair"` is the *waiting* answer, the least severe of the five,
>   and it sits last.
>
> * **Where `credentials-rejected` comes from.**  Not from the engine's
>   inference: upstream libjuice consumes the TURN Allocate error code
>   inside `agent_process_turn_allocate()` and drops it, so "the server
>   refused my credentials" and "the server was unreachable" are
>   indistinguishable from the outside.  A refused credential is exactly
>   the case a host most needs to name (refresh the credential vs. fix
>   the network), so the fact has to reach the surface.  It reaches it
>   through the **seam**: `IICETransport::turn_failure_reason()` (a
>   default-implemented addition, so no existing implementer breaks), fed
>   by a narrow vendored patch
>   (`src/third_party/libjuice/patches/0003-turn-allocation-failure-reason.patch`)
>   that classifies the failure **where it is still known** — 401 is a
>   credential problem, 438 a stale nonce, the "transport could not be
>   opened" flag a transport problem — and hands the host a *category*
>   rather than a raw STUN error code.
>
> **The evidence.**  `tests/test_engine_connectivity_diagnostics.cpp`
> builds each of the six reasons and pins the priority order;
> `src/modules/ice/tests/test_ice_diagnostics.cpp` stands up an in-tree
> TURN server and shows the **401 → `credentials-rejected`** path and the
> **unreachable → not-credentials-rejected** path, which is the pair
> that proves the seam is worth having.

### N1 — real TURN/TLS (RFC 6062)

**Done when:** a session through a TURN server that **only accepts TLS on
port 5349** establishes, the control stream's TLS handshake is visible in
the stats (`turn_transport_used == "tls"`) and in the server log, and the
**negative control** — the same test against a server with TLS disabled —
**fails to connect**.

**The mechanism.**  TURN-over-TLS is TURN-over-TCP wrapped in TLS
(RFC 6062 §3.2; the RFC 8656 §12.4/12.5 framing inside is already
implemented by libjuice's `turn_tcp`).  Three pieces: a TLS client for the
control stream (§5 **N1-1**: which stack, **N1-2**: where it lives — a
`turn_tls` collaborator inside the ICE module, **and libjuice carries a
narrow patch**); the certificate rule the DTLS path already uses (pinned
fingerprint, or the trust store with `TurnServer::tls_server_name` for
SNI); and honesty in the seam — `turn_transport_supported(Tls)` becomes
`true` **only in a build that actually has the TLS stack**, and a build
without it keeps today's warning.

**Scope boundary.**  RFC 5766 long-term credentials only; no alternate
auth, no TURN-over-DTLS.

> **Update 2026-11-26: N1-2 is answered — Option A, and libjuice does carry
> a patch.**
>
> §5 **N1-2**'s original default was "libjuice is not patched".  That
> default was **not implementable**, and the reason is worth writing down
> because it is not obvious from the plan's own text: upstream libjuice
> *has* the `JUICE_TURN_TRANSPORT_TLS` enum value, but its handling of it
> is a **downgrade** —
>
> ```c
> if (turn_server->transport == JUICE_TURN_TRANSPORT_TLS) {
>     JLOG_WARN("TURN over TLS is not supported, falling back to TCP");
>     entry->turn->transport = JUICE_TURN_TRANSPORT_TCP;
> }
> ```
>
> So "no patch" could only have meant "no real TLS": a client that wanted
> TURN-over-TLS would have had to reimplement the TURN protocol itself, in
> NimRTC, next to libjuice's — a second TURN stack, a second set of
> credential handling, a second set of refresh timers.  The two options
> were compared on the facts (§7's **N1-2**), and the decision was
> **Option A**: the TLS client lives in the ICE module
> (`src/modules/ice/src/turn_tls.{hpp,cpp}`), and libjuice carries a
> **narrow seam** (`src/third_party/libjuice/patches/0002-turn-tls-transport.patch`).
>
> "Narrow" is load-bearing, and it is the answer to L5: libjuice still owns
> the TURN protocol, still carries **no TLS stack**, and still does not
> know what a certificate is.  The host hands it five function pointers
> (`connect` / `handshake` / `read` / `write` / `close`) over a
> byte-oriented stream, and libjuice's self-delimiting framing (§12.4 /
> §12.5) never has to understand a TURN message.  The decision and its
> alternatives are recorded in **ADR-027**; the patch's provenance and how
> to regenerate it are in `src/third_party/vendor.json`'s libjuice note.
>
> **The seam removes the downgrade, and that is why it exists.**  A
> `JUICE_TURN_TRANSPORT_TLS` server with no usable TLS client now **fails
> the allocation** instead of quietly opening a plain TCP control
> connection and sending the TURN long-term credential in the clear.  The
> observable outcome is "no relay candidate", never "a relay candidate
> obtained over an unencrypted control connection".
>
> **What this does not change.**  N1's *done-when* is unchanged, and N1
> remains **CLOSED** (§0a).  This update amends the **decision record**
> only — the plan's §5 text and §7's row said "libjuice is not patched",
> and ADR-027 had been referring to "§5 (N1-2, as amended)" for a
> decision that had never been written back.  A plan that records a
> default the tree contradicts sends the next reader to do the wrong
> work.

### N2 — ICE-over-TCP candidates (RFC 6544)

**Done when:** two peers that can only reach each other over TCP nominate
a TCP candidate pair, and the selected pair's `protocol` reads `"tcp"`.

**The mechanism.**  `IceTransport` gathers host TCP candidates with an
active / passive `tcptype` (RFC 6544 §4.5) prioritised against UDP (§4.3);
the **SDP writer** emits `a=candidate:… tcp <pri> <host> <port> typ host
tcptype passive` — the piece that does not exist anywhere in the tree.
§5 **N2-1**: TCP is attempted **after** UDP fails, not raced with it.

**The test.**  A loopback test where the UDP sockets are bound to
addresses that cannot route to each other and TCP is the only path — the
shape of a TCP-only firewall, deterministic in CI.

### N3 — reconnection policy (the consolidated ICE-restart state machine)

**Done when:** a simulated network change (the local address moves)
recovers the session **without the host calling `restart_ice()`**, the
restarts are bounded, and there is exactly **one** policy in the engine.

**The mechanism.**  A named private collaborator
(`src/engine/src/engine_ice_recovery.{hpp,cpp}`, the same shape
`FeedbackGuard` took in v1.3.0): a grace window on `Disconnected`, an
exponential backoff with a cap, a **terminal** state when the cap is
reached (reported, not looped), driven by the engine's own ICE state.
`restart_ice()` stays as the manual entry point and counts against the
same budget; its documented two-step contract (`restart_ice()` then
`send_to_peer(create_offer())`) does **not** change — N8 is what makes
the second half *automatic* for the host.  Numbers in §5 **N3-1**.

### N7 — credentials as a first-class seam

**Done when:** an engine opened with a **TURN credential provider** starts
gathering before the host has fed it anything else; the provider is
**re-consulted when the credential expires or the relayed path drops**, and
a refused credential is reported as `"credentials-rejected"` (N4's
vocabulary) rather than as a generic ICE failure.

**Why it is not "already covered by `add_turn_server()`".**  Today the
host must call `pre_open()` → `add_turn_server()` → `open()`, in that
order, with credentials it has already fetched — three lifecycle rules that
every host gets wrong once, and a TURN credential with a short TTL
(remote-desktop I4 already issues one) **expires mid-session**, at which
point nothing refreshes it.  N7 makes the credential *pull* the engine's
job: a provider callback (`turn_credentials()`), consulted at gathering
time and at every allocation the agent has to make again.  The RFC 7635
style username/password says nothing about the lifetime — real-time
TURN credentials do (`username:timestamp` + HMAC) — so **the lifetime is
the provider's business and the engine must ask again**.  §5 **N7-1**.

**What stays the host's.**  *Who* issues the credential (the signalling
service, an auth server) — RD-7.  N7 is the seam, not a server.

### N8 — the path change is reported, and the host can act on it

**Done when:** when N3's recovery moves the session to a new pair (a new
local address, a relayed path after a direct one, or the reverse), the
host is **told** — with both pairs, not a boolean — so its signalling can
re-offer when the peer has to learn the new credentials.

**The load-bearing fact this rests on.**  A local restart changes the
**credentials** *and* the **ufrag/pwd**, so by RFC 8445 §9.1.1.1 the peer
must be renegotiated — there is no way for the engine to fix the far end
alone.  The v1.2 plan's C3 ("unify the reconnection policy") is therefore
**not** satisfiable as a transport-only fix; it is exactly N3 + N8.  §5
**N8-2** records whether the engine may *hint* the re-offer (an offer
fragment the host sends) or only *report* it — the default is *report*,
because the SDP exchange is the signalling's.

**Why this is a separate item.**  N3 restarts *locally*; the peer can only
observe a restart through the SDP that carries the new credentials
(RFC 8445 §9.1.1.1), which means the *host's signalling* has to be
involved.  The tree already has the **peer's** half: `set_on_ice_restart`
fires when the peer's description carries new credentials.  What is
missing is the **local** half — which pairs, and why — and the reason:
without it the host cannot tell "recovering" from "recovered" except by
polling `Stats::transport.selected_pair` and diffing strings.  The report
carries the **old pair, the new pair, the reason**
(`"local-address-changed"`, `"peer-restart"`, `"relay-fallback"`) and the
number of restarts so far; `set_on_ice_restart` keeps its exact meaning
(the peer's SDP changed) and gains the pair detail in the same struct.

### N9 — the library installs, a host finds it, and every platform leg proves it

**Done when:** a host project on **Windows, macOS and Linux** does
`find_package(NimRTC REQUIRED CONFIG)`, links `NimRTC::engine`, and builds
the N6 sample **against the installed tree only** — no source checkout, no
build-tree paths — and the release bundle carries the same exported config.

**What is already true.**  The Windows (MSVC) and Linux jobs already stage
an install and build an out-of-tree consumer (`ci.yml` "Install +
downstream proof"), so the export path is not hypothetical.  **The macOS
job (`macos-clang`) builds and tests in-tree but has no install +
downstream proof step**, and the macOS leg carries three v1.4.0 claims of
its own (D2's Metal renderer, D3's default table, D4's AVFoundation
camera).

**What N9 adds:** the same install + downstream proof on `macos-clang`,
and the export fixes the proof uncovers on that leg.  The bundle format is
§5 **N9-1** — the default is a plain archive of the install tree, because
a package format is a distribution decision and not an SDK one.

### D1 — the engine runs the device layer

> 那张表里，是因为那张表列的是**只写模块目录**的条目，而 D1 碰

**Done when:** with **no device ids configured**, an engine opened with a
"conference" config captures from the default microphone, plays decoded
audio to the default speaker, and reports both devices in the stats —
on all three platforms, with the synthetic device standing in on CI.

**The mechanism.**  Three additions, all of the same shape the video
capture path already uses (`video_capture_name` + the pump):

1. **A registry category for the device seams.**  `kAudioSource` /
   `kAudioSink` join `kVideoCapture` in `core::Registry`, and
   `register_all_default_plugins()` registers the PortAudio-backed
   factories, so `open()` has something to resolve.
2. **Engine config:** `audio_source_name` / `audio_sink_name` (empty =
   the default device; `"none"` = the explicit opt-out, so a host that
   feeds PCM by hand keeps working unchanged), plus the device config
   (`AudioSourceConfig` / `AudioSinkConfig`) alongside the existing
   capture config.
3. **The engine's audio device pump** — the audio counterpart of
   `engine_video_pump.cpp`: pops capture frames on the tick thread and
   hands them to the outbound path; writes decoded PCM to the sink **and**
   reports the sink's `played_samples()` to `set_render_delivered()` (the
   3A reference alignment F3/F4 built, now wired by the engine rather than
   by the host).  RD-6 holds: the device owns its thread, the engine
   touches the codec and the 3A only on its own.

**The seam changes are additive** — the seams already exist and are
STABLE; what changes is *who* drives them.  A host that keeps driving
them by hand sets `"none"` and loses nothing.

### D2 — the engine runs the renderer

**Done when:** with `video_sink_name = "auto"` (the default), a decoded
frame reaches the screen on all three platforms through the engine — the
host never touches D3D11 / Metal / EGL.

**The mechanism.**  `EngineConfig::video_sink_name` (empty or `"auto"` =
the platform renderer resolved through the registry; `"headless"` / an
explicit id keeps today's behaviour for a recorder or a test).  The
renderer factories (`video_sink::register_default_plugins()`) register the
platform sinks, and the engine already has the GPU mailbox
(`engine_gpu_mailbox.hpp`) and the scale-to-fit math
(`video_aspect_fit.hpp`) — D2 is the **selection** plus the wiring that
the `rd_viewer` example does by hand today.  The render clock (v1.3 Q6)
runs **inside** the sink, which is what the Q6 seam was built for.

### D3 — default device policy

**Done when:** the same binary, run with no arguments, captures the
screen, opens the microphone and the speaker, and renders the peer's
picture — on Windows / macOS / Linux.

**The mechanism.**  The per-platform default table that lives in
`rd_device.cpp` today (`windows-wgc` / `macos-screencapturekit` /
`linux-x11`, the camera default, the audio defaults) moves into the
engine as **one documented policy** with the same override rules the
profile system already uses (`EngineConfig` values win over the policy;
an empty value means "the policy").  This is what makes "no device ids
configured" meaningful rather than a trap.

> **2026-11-27 update: D3 is landed.**  The table is in the engine:
> `src/engine/src/engine_device_policy.{hpp,cpp}` owns it and
> `NimRTCEngine::default_device_policy()` is the public read of it (a
> `DevicePolicyInfo` struct — screen / camera capture backends plus the
> audio ones).  `examples/remote-desktop/rd_device.cpp` now *reads* that
> policy instead of keeping a second copy of it; a second copy of the
> table is a second thing that can be wrong.
>
> **One new config value: `"auto"`.**  The plan said "an empty value
> means the policy", but the tree already gave the empty string a
> meaning of its own: **the host feeds the frames itself** (the
> engine-driven capture path is skipped).  Changing that would have
> broken every host that relies on it, so `"auto"` is the value that
> asks for the policy.  An **explicit id always wins** over the policy.
>
> **The content hint picks screen vs. camera.**  `ContentHint::kText`
> means "the content is text", which is the screen-sharing case, so it
> selects the screen backend; every other hint (including
> `kUnspecified`) selects the camera.
>
> **A policy that cannot be honoured is not an error.**  If the policy
> names a backend that this build does not have, the engine degrades to
> "no capture device" and *warns* (`PluginFailureMode::Warn`) rather
> than failing the session — a CI machine has no camera, and that must
> not be a hard error.  An unknown **explicit** id is still a
> configuration error (`kVideoCapturePluginMissing`), because there the
> host asked for something specific and did not get it.

### D4 — camera and hot-plug

**Done when:** a camera unplugged mid-session fails **cleanly** (a
reported error, no stall), a camera plugged in afterwards is reopened,
frames resume, and the counters say so — and a camera selected by
*default policy* works on each platform.

**The mechanism.**  The capture seam gains an enumeration / change
notification (device added / removed) that the engine's capture pump
polls per tick (no new engine thread, RD-6); the reopen is backoff-bounded
(the pump reopens once today, `video_capture_restarts`); the counters gain
`video_capture_device_changes`.  The camera class (Media Foundation /
AVFoundation / V4L2) gains the device-removed / device-restored paths the
screen backends already have (DXGI device-lost).

> **2026-11-27 update: D4 is landed.**  The change notification is an
> **optional** seam: a *separate* interface,
> `plugins::ICaptureDeviceEventSource`
> (`src/plugins/include/nimrtc/plugins/capture_device_events.hpp`), so
> `plugins::IVideoCapture` — a STABLE header — gains **no** pure
> virtual function.  The engine probes for it with a `dynamic_cast` and
> falls back to its own enumeration when the device does not offer it.
>
> **Device health is not the frame pump’s job.**  The plan put the
> polling "in the capture pump", but the pump returns early when there
> is no encoder or no sender — so a session with no video would never
> have noticed a camera being unplugged.  Both
> `poll_capture_device_changes()` and `recover_capture_device()` now sit
> directly on the engine’s main `tick()` loop, which is where RD-6
> wanted them anyway (no new engine thread).
>
> **The reopen is backoff-bounded.**  1 s base, doubling to an 8 s cap,
> at most 20 attempts; after that the engine stops retrying and fires
> `kVideoCaptureOpenFailed` once.  A successful reopen resets the
> budget.  Two independent counters make it observable:
> `video_capture_device_changes` (a device appeared or went away) and
> `video_capture_restarts` (a reopen happened).

### D5 — audio P2: DTX coupling and the 3A contract

**Done when:** a DTX-enabled sender and a peer that negotiated DTX produce
a silent stretch the receiver handles as **silence** — `frames_concealed`
does not move — and a *lost* DTX frame **does** conceal (the negative
control); the 3A reference alignment holds on a real device.

**The mechanism.**  The audio plan's WP-12, unchanged in intent.  The
encoder already counts `dtx_frames` (`src/modules/opus/`); `audio_rx`
never mentions DTX — concealment cannot tell a suppressed frame from a
lost one.  D5 is the **coupling**: the DTX signal travels where the
concealment can see it, and the contract with D1's playback reporting is
stated once.  §5 **D5-1**: DTX default stays **off**, switchable per
stream (flipping a default that changes how every call *sounds* is not an
adaptation item).

### D6 — the connectivity profile: the "no connectivity policy" half of the call

**Done when:** an engine opened with a **named profile** — `"conference"`
or `"remote-desktop"` — and nothing else establishes a session on the
"networks a real user has": STUN session-traversal, **TURN/TLS on** when a
credential is available or immediately when gathering says a relay is
required, **TCP fallback after UDP fails** (N2-1), and N3's recovery
policy armed.  With no STUN / TURN reachable it still tries and **reports
what it tried** (N4's vocabulary), instead of silently degrading.

**The mechanism.**  A `connectivity_profile` key in `EngineConfig`
(`"auto"` = the default, which is *on*, because a connectivity policy that
has to be switched on is not adaptation).  The profile carries the
**policy defaults**, not the seam values: the host's explicit keys
(`connectivity.stun_servers` / `turn_servers` / `N8` provider) still win.
This is what N6's sample consumes instead of writing the ICE policy.  §5
**D6-1**.

**Why not fold it into D3.**  D3 is *defaults for device ids*; D6 is
*defaults for connectivity*.  They fail in different ways on different
hosts (a CI machine has no camera; a corporate machine has no STUN), and
keeping them separate keeps each one's evidence honest.

> **2026-11-27 update: D6 is landed.**  `EngineConfig::connectivity_profile`
> (default `"auto"`, which is *on*) names a policy; the engine applies
> the profile's defaults before opening the transport, and the host's
> explicit STUN / TURN keys **win** — a profile only fills in the keys
> the host left unset.
>
> **The profile carries intents, not addresses.**  Its keys are `stun`
> (a boolean), `turn_tls` (`"always"` / `"when_available"` / `"never"`)
> and `tcp_fallback` (a boolean) — the *shape* of the policy, not the
> servers it points at.  So the table the engine obeys lives in code
> (`src/engine/src/engine_connectivity_profile.cpp`), and
> `profiles/connectivity/connectivity-profiles.json` is the
> **documentary** twin of it.  That file sits in a **subdirectory** on
> purpose: the `*.json` files directly under `profiles/` are *engine*
> profiles, and the assembly module validates every one of them against
> `profiles/schema/profile-v1.2.json` — a "name → defaults" map is not
> an engine profile and would fail that schema for missing `name`.
>
> **The default STUN server is `stun.l.google.com:3478`.**  The plan
> said the `"auto"` profile "is on" without saying which server that
> meant; the engine is an SDK, so a host should not have to know a
> public STUN server's name to get a server-reflexive candidate.  The
> four places in the tree that already hard-coded it were all in
> **examples** — which is the D3 complaint ("the SDK's default policy
> lives in an example") applied to STUN.  When the public server is
> unreachable the engine still works; it simply has no srflx candidate,
> and N4 reports `no-candidates`.  That is **honest reporting**, not an
> error.
>
> **The evidence.**  `tests/test_engine_connectivity_diagnostics.cpp`
> asserts the default profile, that the profile configures the default
> STUN server, that the host's own STUN server wins, and that an unknown
> profile name falls back to `"auto"` rather than refusing to start.

### D7 — the app-convenience surface

**Done when:** a host that never touches a pipeline can run the whole call
through: a **one-call lifecycle** (`start(config)` / `stop()` /
`hangup(reason)` that closes devices, the transport and the signalling
hook in a defined order), **one call-state callback** spanning the whole
stack — `connecting` → `connected` → `reconnecting` → `failed` /
`closed` — with the N4 / N8 detail attached, the **control-event
callback re-exported** beside it (`set_on_control_message` exists and
keeps working; D7 only makes the two callbacks read as one surface), and
**one error code per failure** a host can act on (a non-empty
ICE/DTLS/media reason on every `closed` transition).

**What exists today, and what D7 adds.**  `set_on_state_change` already
delivers the raw ICE state as a *string*, `set_on_control_message` already
delivers the operator's bytes, and `set_on_error` already carries an error
code.  What is missing is the **join**: one ordered state machine over
the whole engine (a restart inside N3, a DTLS failure and a hangup are
three things a host must derive from three separate observations today),
and the reason attached to the transitions a host actually branches on.

**Why this is not "nice to have".**  The stats suite (`get_video_stats()`
and the transport stats beside it) is the *diagnostic* surface by design;
a host that wants "is the call up?" must today poll `ice_state_string()`
(or `set_on_state_change`) and diff `Stats` — and the remote-desktop
example does exactly that, which
is how we know it is the host's own work, not a convenience.  A commercial
SDK's "few lines" includes *knowing what happened*.  The work is **wiring
that follows the existing non-callback surface's rules**: the callbacks
carry *state transitions, counters and enums*, never a new high-frequency
event stream and never a new sink, so D7 does not reopen a performance
question — it only names what is reported and when.  The host's thread
rule is the existing one (callbacks run on the tick thread the host
already owns or that the DEFAULT policy owns; a host that owns the clock
gets the events on its own thread).  §5 **D7-1**.

## 5. N6 — the SDK claim

**Done when:** one sample application, **≤ 200 lines of C++**, establishes
an audio + video + control call between two machines through the
reference signalling service, across a NAT that only relays over TLS, with
no device ids configured, no renderer code, and no connectivity policy —
and it is **run by CI's acceptance leg** (two processes on one host behind
the simulated NAT; the real two-machine run is the archived evidence).

**What the host writes.**  A signaling exchange (offer / answer /
candidates — the reference service's client already does this in
~200 lines of Python, and the C++ side is the `rd_signalling.hpp` shape),
an `EngineConfig` that names the profile (D6), callbacks for "call state",
"control event" and "path changed" (D7 / N8), a TURN credential provider
(N7), and the N8 re-offer on the peer's side.  Everything else — devices,
codecs, BWE, RTX, recovery, rendering, AEC — is the engine's.

**Why 200 lines is the bar and not a slogan.**  It is the size the
signalling exchange needs *alone*; the claim it proves is that the
application contributes **nothing but signalling and product UI**.  The
number is re-measured on every run by the acceptance script (it counts the
sample's non-comment lines and fails if the count grows by more than 10 %
without the plan being amended) — a limit that drifts is a claim that
drifted.

**The evidence.**  Same honesty rules as the soak and hardware recorders
(v1.3 Q5 / Q7): the verdict is re-derived from the archived numbers; a
dirty tree is marked; "no device on the host" is `SKIPPED`, never `PASS`;
the archive carries the device identity, driver version, and the NAT /
relay configuration.

| **N9-1** | Archive of the install tree, or a per-platform package? | **Archive** (a zip / tar of `install/`); a package format is a distribution decision, and the CI proves `find_package` works either way |
| **D6-1** | Is the connectivity profile on by default? | **Yes** — `"auto"` means STUN on, TURN/TLS when credentials exist or gathering requires a relay, TCP after UDP, N3 armed.  A host that wants to own the policy sets explicit keys and wins |
| **D7-1** | How does the host learn "which failure"? | A **small stable enum** (`kIceFailed`, `kDtlsFailed`, `kTurnRefused`, `kCredentialsRejected`, `kMediaFailed`) plus the string reason N4 already defines — the enum is what a `switch` can act on, the string is what a log carries |
| **N5-2** | How does CI reach the reference TURN server: a container, or a native install? | **Native `coturn` on the Linux leg** (the hosted runners have no Docker daemon), `-c <config>`; the compose file stays the developer / archived-evidence path.  The test only sees a TURN URI + credential.  **Written 2026-11-20** as `linux-turn / reference TURN server`; it asserts a verified TLS handshake, a real TURN allocation over it, and the negative control on the *same* port |
| **N8-2** | On a local recovery, may the engine *hint* the re-offer (produce the offer fragment), or only *report* the new pair? | **Report only.**  The SDP exchange belongs to the host's signalling; the engine hands it the pair, the reason and `create_offer()`'s existing contract |
