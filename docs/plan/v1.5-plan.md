## 0. The claim this release has to make true

> **A session on a bad link degrades in ways the network asked for, and
> recovers without the receiver begging for keyframes.**

v1.3.0 answered loss with **RTX and a feedback bound** (Q3 / Q4): a lost
packet is retransmitted on its own payload type, and a keyframe request
storm is capped.  That is the *cheap* half.  It is also the half that stops
working exactly when it matters: on a link with sustained loss, every
retransmission is another packet on a link that is already dropping, and
the keyframe that repairs the damage is the *largest* packet in the
stream.  RTX + PLI turns a lossy link into a latency problem.

v1.5.0 is the other half:

| Axis | What "survives" means | Exit |
|---|---|---|
| **Loss** | recovery that does not depend on asking the sender to repeat itself: FEC for the losses NACK cannot afford, retransmission *inside* a frame budget for the losses FEC cannot cover, and RTX/FEC told apart in the stats | at a committed loss/delay profile, the freeze count and the p95 latency are **lower than the RTX-only baseline**, measured, not asserted |
| **Layers** | a sender that produces more than one encoding of one source, and a receiver that takes the one the network pays for | two peers negotiate `a=simulcast`; the receiver switches layers without a full renegotiation and without a freeze |
| **Shape** | the engine's video path, RTCP path, audio path and transport path each live in a named collaborator, not in `engine_*.cpp` | `engine_impl.hpp` stays under its line budget, each collaborator has its own test, and `tools/check_engine_layering.py` grows a rule per collaborator |

**Why this is one release and not three.**  The three axes meet in the
*same ten files* (§4), and two of them are **ordered by fact, not by
preference**: FEC changes what the receive-side memory model must bound
(Q2's work), and layers change what RTCP has to say (a layer switch is a
feedback decision, not an SDP one).  The shape work must therefore happen
*around* them and not before them — moving a file that is about to grow
three codecs is how a refactor doubles.

### What v1.4 leaves behind that this plan depends on

| v1.4 item | Why v1.5 needs it |
|---|---|
| **N4** (the failure vocabulary in `Stats::transport`) | the loss vocabulary below extends it, and the same closed-enum discipline applies |
| **N8** (path-change reporting) | a layer switch and a path change are two different reasons a receiver's bitrate falls; mixing them in one stat is how "why is it blurry" stays unanswered |
| **D6** (the connectivity profile) | the loss policy is chosen by profile, like the connectivity policy is |
| **D7** (the call-state surface) | the `degraded` state (below) is a transition on D7's state machine, not a new callback |
| **D1** (the engine runs the device layer) | `AudioPipeline` (§5, `1.5.x`) cannot be extracted before D1, or the device pump moves twice (gap inventory §5.2) |
| **N2 / N3** (ICE-TCP, the restart policy) | `TransportManager` (§5, `1.5.x`) consumes them; extracting it first would move a state machine that is still moving |

### R1 — RED, and the redundancy seam the FEC rides

**Done when:** a sender configured with RED emits `a=rtpmap:<pt> red/…` +
`a=fmtp:<pt> …` in the offer, the receiver reassembles a redundant
payload into the original payload type (RFC 2198 §4), and **the negative
control** — a RED packet whose redundant block is corrupt — is dropped as
one packet, not two.

**The mechanism.**  A new module `src/modules/redundancy/` (RED framing, the
block header, the timestamp-offset arithmetic — the same "format, not
transport" shape `rtx/` has), a **seam** `plugins::IRedundancyCodec` that
the send and receive paths resolve through the registry (id `"red"`),
and the SDP attributes.  The seam is the *only* place a scheme name is
matched: R2's FEC is a second implementation of it, so the engine never
learns what "ULPFEC" is.

**The PT demux.**  The engine's inbound demux currently routes by
negotiated PT; RED and the FEC PTs are **associated** payload types
(`a=fmtp:<fec-pt> …`) that the demux must route without treating them as
media.  This is the piece that does not exist in the tree (the 2026-11-14
survey's "PT demultiplexing" covers media only).

**§8 R1-1** decides the RED default (default: **off**, switchable per
stream — RED costs bytes on a good link, and v1.3's evidence is that the
good link is the common case).

### R2 — FEC: ULPFEC and FlexFEC

**Done when:** with FEC enabled on a committed loss profile (`--profile
hostile`, 5 % loss / 80 ms / 40 ms jitter / 10 % reorder — the v1.3 Q5
profile, so the two releases' evidence compares), the receiver recovers
a lost packet **from the FEC stream**, the recovery is counted as
`fec_recovered` and **not** as an RTX retransmission, and the NACK rate
falls against the RTX-only baseline on the same profile — both artifacts
committed.

**The mechanism.**  Two implementations of R1's seam:
`ulpfec` (RFC 5109: XOR over a mask, one protection packet per group) and
`flexfec` (RFC 8627: the interleaved/burp shape and its SDP
`a=rtpmap:… flexfec-03`).  Protected-by / ssrc-group negotiation in the
SDP.  The **sender's** policy (how many protection packets for how many
media packets) is a budget: a fixed overhead percentage, capped, clamped by
the pacer's rate — it reads `plugins::IPacer`, it does not implement one.

**ULPFEC before FlexFEC, in the same item, in that order.**  ULPFEC is the
smaller format and it is the one a browser-shaped peer expects; FlexFEC is
the one that recovers *across* a burst instead of cost one protection
packet per group.  Both behind the same seam means the item ships in two
commits without a second design review.

**§8 R2-1** decides the default (default: **on for the `conference` and
`remote-desktop` profiles at 20 % max overhead**, off otherwise).  The
numbers are §8 R2-2's.

### R3 — the layering model: encodings inside a stream

**Done when:** `VideoStream` carries an **encoding list** (id. `rid`, SSRC,
payload type, resolution, target share) instead of one encoding; the legacy
single-encoding path **is** the list of one, and the byte-for-byte identity
the multi-stream API already promises extends to it; a stream with several
encodings reports per-encoding stats.

**The mechanism.**  `src/engine/src/video_stream_set.hpp` already says the
room is there ("the encoding list of a stream is a list of encoders, not a
single encoder") — R3 fills it.  The `plugins::IVideoEncoder` seam does not
change: an encoding is an encoder instance plus a share, exactly as a
stream is an encoder instance plus a share today.  The **`a=rid` /
`a=simulcast` SDP** stays in R4 — R3 is the model and the engine's plumbing,
and it is testable with no negotiation at all (a synthetic three-encoding
stream sends three SSRCs; the receiver's existing SSRC demux already
handles them, per `engine_timeline.cpp`'s RFC 5956 comment).

**Why this is not "simulcast" yet.**  The model is the part R5 (the split)
and R6 (the receive half) both build on, and it is the part that must land
without touching SDP — so that if R4 needs a decision it does not need
*this* decision too.

### R4 — simulcast negotiation and layer selection

**Done when:** two NimRTC peers negotiate `a=simulcast:send l,h,q` +
`a=rid:` lines (RFC 8853 §5.1, §6) in offer and answer; the sender sends
three encodings; the receiver **switches layers** (its requested `rid` in
the answer, then a feedback-driven switch) without renegotiation and
without a freeze; a layer the receiver does not request is **not sent** at
full rate; and the selected layer is named in the stats.

**The mechanism.**  The SDP writer + parser gain `simulcast` and `rid`;
`src/engine/src/video_rtx_negotiation.hpp` grows a sibling
(`video_simulcast_negotiation.hpp`); the switch is driven by the BWE
estimate and **hinted** over the feedback channel — the RTCP half is
**A2's** to carry, and R4 lands with a minimal hint in `engine_rtcp.cpp`
that A2 later moves.  That is deliberate: A2 is in wave 3, after R4, so
the hint exists when the extraction happens instead of being invented
during it.

**The browser question is a decision, not a detail.**  Chrome's simulcast
SDP is a family of dialects (§8 R4-1); the default is **NimRTC↔NimRTC
first**, browser interop as a follow-on item in the same plan, because
`RTCPeerConnection` interop is a separate contract the product has not
taken (v1.4 §2a's exclusion table).

### R5 — the multi-encoding ladder split

**Done when:** with three encodings on one stream and one estimate, the
split is **documented, unitary and tested**: the money (the stream's share)
is divided between encodings by weight with the largest-remainder rule the
audio / video split already uses (`src/engine/src/bandwidth_allocation.hpp`
— *one rule, not two*), the ladder's level changes move encodings in a
defined order (high → low), and a resolution-floor rule keeps at least one
encoding above the floor.

**The mechanism.**  `compute_video_stream_shares()` is already "called once
per tick, one function" — R5 adds a second call level, not a second
function shape.  The ladder itself (`src/modules/video_bitrate_control/`)
does not change: each encoding owns one ladder.

### R6 — the receive half of SVC (spatial layers)

**Done when:** a **VP9** spatial-layer stream (SS structure, RFC 9628's
dependency descriptor) is received and the receiver decodes *up to* a
requested layer, switching up and down without a freeze, and reports the
layer it actually decodes.

**Why VP9 and why after R4.**  VP9 SVC is the only SVC the tree has a codec
for (`src/modules/vp9/` exists; `libvpx` is vendored), and its
*receive* half is a decoder-side concern the profile can select.  The
**send** half (producing SS) is **not** in scope — AV1 SVC would need the
encoder V2 ships, and VP9 SVC send is a codec-side change the ladder does
not need.  **AV1 SVC** (the `av1` codec's scalability mode) is recorded in
§7 as deferred with its reason.

> **§8 R6-1 decides whether SVC receive is in `1.5.0` at all.**  The
> default is **yes, receive only**: it is the cheapest way to prove the
> receive-side model (R3) is layer-generic rather than simulcast-shaped,
> and it costs one module's test suite.

### R7 — the measurement

**Done when:** on the committed hostile profile, three numbers are
reported side by side and committed as an artifact: **RTX-only** (the
v1.3.0 baseline), **RTX + FEC**, and **RTX + FEC + simulcast (two layers
available, one requested)**.  The artifact reports freeze count, p95
end-to-end latency, NACK rate, FEC recovery count and layer switches — and
the release's headline is that the second and third **do not lose to the
first** on any of them.

**What this closes.**  `remote-desktop-plan.md` §B.4 M3's remaining open
item is "the fixed-bitrate *baseline* comparison run on real hardware"; R7
closes it with the right baseline (RTX-only) and *names the substitution*,
because a fixed-bitrate baseline measures the ladder, which M3(a) already
proved, and not the loss story this release is about.

### A1 — `VideoPipeline` (wave 1)

**Done when:** the video source / codec / sender / receiver / sink

### V1 — national-crypto SRTP (`1.5.x` minor)

## 3. The ordering question — what is serial, what is parallel, and why

This section exists because the obvious question ("is the resilience work
before or after the architecture work?") has a longer answer than "before",
and the longer answer is a **dependency list**, not a preference.

### 3.1 Serial by fact

| Constraint | Why it is a fact |
|---|---|
| R2 after R1 | FEC is an implementation of the redundancy seam and the PT wiring R1 creates |
| R4 after R3 | a switch needs encodings; the model is R3's |
| R5 after R4 | the split is between encodings negotiation produces |
| R6 after R4, R5 | the receive half needs a layer set and a share rule to exist |
| R7 after R2, R4 | the measurement compares against FEC and layers |
| **A3 after v1.4 D1** | the device pump is D1's; extracting the audio path first moves it twice (gap inventory §5.2) |
| **A4 after v1.4 N2–N3** | the recovery state machine is N3's; `TransportManager` is where it lands, not where it is invented |
| **A2 after R4** | the layer hint is R4's first, minimal, in `engine_rtcp.cpp`; A2 carries it afterwards, so it is not invented during a move |

### 3.2 Parallel — and how the parallel work is kept apart

A1 and R1 (wave 1) write **disjoint surfaces**: A1 moves video-path
behaviour, its *seams* and its *stats*; R1 adds a module, a seam and the
inbound PT demux.  The one file they meet in is the inbound demux's
translation unit, and R1 owns that file for the wave.

A2 (wave 3) and A4 (`1.5.x`) are **serial against track R's end**: A2's
last behaviour is the layer hint, and A4's state machine is v1.4's.  Running
either against a moving R is the "two directions editing one file" the v1.4
plan §8a rules out — the same rule applies here.

### 3.3 The lane is independent

V1 – V4 write **outside** `src/engine/src/`'s video and transport paths:
V1 is `srtp/` + `EngineConfig` (+ the engine's selection point), V2 is
`av1/` + CMake, V3 is CMake + docs, V4 is a document.  Each can land any
time on `1.5.x` — which is what makes the lane a *lane* and not a track.

| **R1-1** | Is RED on by default? | **Off, switchable per stream** — it spends bytes on the link that is working, and v1.3's evidence is that the common link works |

## 10. Verification notes — executed, not asserted

Like v1.4 §10, this table is **run**, by a companion script with the same
shape and the same self-test discipline as `tools/check_v14_plan_status.py`:

```
$ python tools/check_v15_plan_status.py
$ python tools/check_v15_plan_status.py --self-test
```

The script exists (`tools/check_v15_plan_status.py`, written with this
plan, **ASCII-only** so it runs under a GBK console code page) and is run
in CI's `windows / msvc` job beside the v1.4 checker (self-test + report).
It
carries the rows currently implemented — R1–R7 and the six **F**
(*foundation*) rows for the tree facts §1 says v1.5 builds on — and its
report is `ok` on every row at the time of writing.  Rows for A1–A4 and
V1–V4 are **added when their items start**: a probe for a symbol that the
item will introduce is only worth having once the item's name is
decided, and a probe written early is a probe that guesses.

**A row flips when its item lands** (v1.4 learned this the hard way: a
row that keeps asserting the absence of a thing that now exists reports
STALE forever).  The flip is made in the script, not here — the table
below is the plan's *narrative*, and the script's `PROBES` table is the
authority.

| Item | Claim the probe makes | Flips when |
|---|---|---|
| F ×6 | the RTX format + negotiation, the keyframe limiter (`video_pipeline`), the split rule, the encoding-room comment, `RtpPacketizer` | never — a foundation that disappears is a regression, and the row reports it |
| R1 | no `IRedundancyCodec` seam · no RED *writer* (the parser already reads a peer's `red/48000/2`) · no `modules/redundancy` | R1 lands → the row expects `present` (for the writer row: `absent` → `present`) |
| R2 | no `ulpfec` / `flexfec` in `src/`, in the SDP or anywhere | R2 lands |
| R3 | `video_stream_set.hpp` has no encoding list | R3 lands |
| R4 | no `a=simulcast` / `a=rid` in the SDP; no `video_simulcast_negotiation` in the engine | R4 lands |
| R5 | no per-encoding share in `src/engine/src` | R5 lands |
| R6 | no spatial-layer receive in `src/modules/vp9` | R6 lands |
| R7 | no committed loss artifact (it names its own markers `rtx_only` / `fec_recovered`) | R7 lands |

**The self-test enforces the one rule v1.4's checker enforces**: every
item the plan marks **CLOSED** has its row expecting `present`.  A row
left asserting `absent` after its item landed is a permanent false alarm.
The clause is pinned against a **synthetic corpus** (a closed item with an
`absent` row *must* be flagged; an open item's rows must *not*), because
today's real table has nothing closed and a rule that is only exercised
the day it first matters is a rule that breaks that day.
