## 一、验收测试里的 3 个 STUN/TURN 协议 bug（已由 zelto 侧代修，需提交人复核）

**位置**：`tests/acceptance/v1-n5-turn-server/acceptance.test.cjs`

这三个 bug 都在**测试代码**里，不在产品代码里。但它们让验收标准 6（coturn 实际可用）永远过不了，
掩盖了真实的产品问题，请提交人确认修法正确并把这三个断言固化下来。

### 1.1 STUN 消息类型编码按 RFC 3489 写，与 RFC 5389 不符

**病灶**：`stunType()` 的位域布局是 RFC 3489（老）的，$C_1$ 放在 bit 11；
RFC 5389 §6 规定 $C_0$ 在 bit 4、$C_1$ 在 bit 8。

```
RFC 5389 §6 布局：
  bit 0-3   : M0-M3   (method 的低 4 位)
  bit 4     : C0      (class 的第 0 位)
  bit 5-7   : M4-M6   (method 的中间 3 位)
  bit 8     : C1      (class 的第 1 位)
  bit 9-13  : M7-M11  (method 的高 5 位)

  type = (mLow | mMid | mHigh | (c0 << 4) | (c1 << 8)) & 0xffff
```

**后果**：Allocate Error Response 本该是 `0x0113`，旧算法算出 `0x0823`。
于是 coturn 返回的 401（带 nonce/realm，需要重试）**认不出来是错误响应**，
测试直接抛 `TURN 响应类型意外: 0x113` —— 401 挑战/重试分支整个被绕过。

**参考值**：

| 消息 | 期望 type |
|---|---|
| Allocate Request | `0x0003` |
| Allocate Success Response | `0x0103` |
| Allocate Error Response | `0x0113` |

**修法**：

```javascript
function stunType(method, cls) {
    const m = method & 0x0fff;
    const c0 = cls & 0x01;            // C0 -> bit 4
    const c1 = (cls >> 1) & 0x01;     // C1 -> bit 8
    const mLow = m & 0x000f;          // M0-M3  -> bit 0-3
    const mMid = (m & 0x0070) << 1;   // M4-M6  -> bit 5-7
    const mHigh = (m & 0x0f80) << 2;  // M7-M11 -> bit 9-13
    return (mLow | mMid | mHigh | (c0 << 4) | (c1 << 8)) & 0xffff;
}
```

### 1.2 REQUESTED-TRANSPORT 属性的协议字节放错了位置

**病灶**：RFC 5766 §14.3 规定该属性是 4 字节，**byte 0 是协议号**
（UDP=17=`0x11`、TCP=6=`0x06`），bytes 1-3 是保留的 0。
原测试发的是 `[0, 0, 0, 0x11]` —— 协议号跑到了 byte 3。

**后果**：coturn 读 `value[0]` 拿到 `0`，判定传输协议未知，
直接回 **400 Bad Request**（`Transport field missing or wrong`）——
测试根本走不到 401 挑战那一步。

**修法**：

```javascript
{ type: STUN_ATTR.REQUESTED_TRANSPORT, value: Buffer.from([0x11, 0, 0, 0]) }
```

### 1.3 XOR-RELAYED-ADDRESS 的 Family 字节读错了偏移

**病灶**：RFC 5766 §6.2 规定该属性值的布局是
**byte 0 = 保留 0x00、byte 1 = Family**（`0x01`=IPv4 / `0x02`=IPv6）、
bytes 2-3 = X-Port、bytes 4-7 = X-Address。
原测试从 `value[0]` 读 Family —— 读到的是保留字节 `0x00`。

**后果**：`decodeRelayedAddress()` 返回 `null`，测试拿不到中继地址。

**修法**：

```javascript
function decodeRelayedAddress(msg, value) {
    if (!value || value.length < 8) return null;
    const family = value[1];              // byte 0 是保留字节
    const port = value.readUInt16BE(2) ^ (STUN_MAGIC >> 16);
    // ...
}
```

**已加的回归断言**（建议保留，3 条分别钉住上面 3 条）：

- RFC 5389 §6：`stunType(0x003, 0x01) === 0x0103`、`stunType(0x003, 0x02) === 0x0113`
- RFC 5766 §14.3：REQUESTED_TRANSPORT 的 byte 0 === 17
- RFC 5766 §6.2：XOR-RELAYED-ADDRESS 的 byte 1 === 0x01（IPv4）

**当前状态**：改完后验收套件 **11/11 通过**（`node --test tests/acceptance/v1-n5-turn-server/acceptance.test.cjs`，0.45s）。

## 二、worktree 里缺 submodule 内容 → 门禁 build 必然失败

**场景**：`zelto gate v1-n5-turn-server` 的 build 命令直接失败：

```
CMake Error at CMakeLists.txt:409 (add_subdirectory):
  The source directory .../src/third_party/nlohmann_json
  does not contain a CMakeLists.txt file.
```

**根因**：`git worktree add` **不带 submodule 的 checkout**。
worktree 里 `src/third_party/*` 只有 `.git` 指针文件，没有实际内容。
而 NimRTC 是重度 vendor 依赖（libjuice / wolfSSL / opus / msquic / googletest…），CMake 直接 `add_subdirectory` 它们。

**后果**：门禁 100% 失败，而且**失败原因与被验的代码无关** ——
人第一反应是「agent 写坏了」，实际是环境没准备好。这是很贵的误诊。

**本次的临时修法**（在 nimrtc 侧手工做的，请提交人固化成流程）：
从主仓把已 checkout 的子模块内容同步过去（robocopy 排除 `.git`）+ 给 msquic 补 `git remote`（SourceLink 需要）。

**建议**：
1. 仓库里加一个 `scripts/sync-worktree-submodules.ps1`（或 `.sh`），
   在 `git worktree add` 之后调用，从主仓 `.git/modules` **本地克隆**（`--reference`，不走网络）。
2. 或者在 `CMakeLists.txt` 里对缺失的 vendor 目录给一条**指名道姓**的错误信息，
   而不是让 `add_subdirectory` 抛一句看不懂的 `does not contain a CMakeLists.txt file`。

> 注：zelto 侧已经在 `core/worktree/manager.ts` 里实现了自动同步（本地克隆，不触网，带超时），
> 但 nimrtc 这边的**手工脚本**仍建议保留 —— 脱离 zelto 单独用 git worktree 时也用得上。

## 三、门禁缺「配置」这一步 → 门禁必然失败

**场景**：子模块问题修好之后，第一次跑 `zelto gate` 又撞上一个：
门禁的 build 命令是 `cmake --build build`，但 `build/` 从来不存在 —— **配置步骤没人做**。

**根因**：`.zelto/config.yaml` 的 `gate.commands` 只有 build / test，没有 configure。
C++ 项目是「配一次、用很多次」，但配置里没有这一段。

**后果**：同上 —— 门禁失败原因与被验代码无关。

**建议**：在 `gate.commands` 里补上 configure 段，例如：

```yaml
gate:
  commands:
    - name: configure
      command: cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
    - name: build
      command: cmake --build build --config Debug
    - name: test
      command: ctest --test-dir build --output-on-failure
```

## 四、`docs/` 里计划与需求的追溯缺口（zelto 侧已补，请复核）

**病灶**：v1-n5-turn-server 的切片规格初稿里，验收标准写的是：

> 1. 实现一个基本的 TURN 服务器，支持 RFC 5766 规定的核心功能；验证方式：通过标准 TURN 客户端测试工具验证基础连接和转发功能

而计划里 N5 的真实内容是「**部署** coturn 参考实现，带 `--require-tls` 拒绝明文 TCP」。
**方向都反了** —— 一个是「实现服务器」，一个是「部署参考实现」。

**根因**：`SliceSpecInput.requirements` 只有需求条目的 **id 列表**（`["N5"]`）。
模型拿到 "N5" 这两个字，只能写通用套话。更根本的问题是：**切片的 `trace.requirements` 当时是空的** ——
需求条目的正文在已确认的需求文档里，但从没被连到切片上。

**后果**：规格是套话 → 门禁照着套话验收 → agent 照着套话实现 →
实现了「一个 TURN 服务器」，而人想要的是「一份 coturn 部署」。
**整条链都在错，但每一步看起来都通过了** —— 这是可追溯性最强的反例：
链是通的（每片都有规格、规格都有验收标准），但内容是空的。

**zelto 侧的修法**（已生效）：
- 从**已确认**的需求文档里抽取条目正文，注入 spec 生成的 prompt；取不到就如实标「找不到」，不编造。
- `version start` 建切片时**自动推导** `trace.requirements`（从切片标题找 `N5`/`D3`/`N2-1` 这类 token，
  **核实它在需求文档里真的存在**才写进去 —— 填了不存在的出处比不填更糟）。

**请 nimrtc 侧复核**：
- `docs/zelto-场景功能地图.md` 里的需求条目**正文**写得够不够具体？
  条目只有一句话的话，spec 生成还是会退化成套话。
- N5 这类条目建议写成「可静态核验」的形态，例如
  「`apt-get install coturn` 可用；`/etc/turnserver.conf` 里含 `--tls-only`；明文 TCP 端口不通」。
