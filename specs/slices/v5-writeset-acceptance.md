# Slice: v5-writeset-acceptance

## 目的
把 M1–M4 四片的**写集边界断言**从「读未提交的工作区差异」改成**状态无关**的判据。

现状（实测 D-68，2026-11-18）：四个验收套件在**已提交的干净树上必红**。

```
v1-video-processing  pass 1  fail 3
v2-ai-decision       pass 5  fail 1
v4-ai-teammate       pass 7  fail 1
v4-voice-agent       pass 7  fail 1
```

四个失败是同一个病灶：断言读的是 `git diff --name-only`（工作区 vs 索引）。
切片一旦被提交（`feat(<id>): slice approved`），工作区差异为空 →
「写集内必须存在已追踪文件的改动」这条断言必然不成立。

这不是「测试写得不对」这么轻：**验收测试自己把「已交付」的状态判成「没交付」**。
合并前在 worktree 里跑是绿的（工作区有差异），合并后 / CI 里跑是红的 ——
门禁②验证的东西与签字之后的状态不一致。

判据要改成**与状态无关**的形式（ADR-075）：
- 「本片改了哪些文件」→ 读**改动清单**（历史 + 工作区）；
- 「本片该有的产物在不在」→ 读**状态**（`git ls-files`，产物在树上就在树上）。

**关键**：「产物在不在树上」是**状态**，
而「这次切片改了哪些文件」是**历史事件**（合并前后不一样）。
把两者混为一谈，就会写出「合并策略一变，判定就翻转」的判据。

## 设计
写集边界要回答两个**不同**的问题，各用各的判据形态：

| 问题 | 判据形态 | 为什么 |
|---|---|---|
| ① **越界检查**：本片改了哪些文件？有没有跑到写集外？ | **改动清单**（历史 + 工作区） | 「改了哪些文件」是**历史事件**，合并前后不一样 |
| ② **产物检查**：本片该有的产物在不在？ | **状态**（`git ls-files`） | 「产物在不在树上」是**状态**，合并前后一样 |

### ① 越界检查：改动清单 = 三个来源并起来

| 来源 | 什么时候有 | 覆盖什么 |
|---|---|---|
| 工作区未提交差异（`git diff HEAD --name-only`） | agent 正在干活时 | 还没提交的那部分改动 |
| 本片自己的提交（`Refs-Slice: <id>` trailer 或 `feat(<id>): slice approved` 标题） | 合并前提交之后 | 本片已提交的改动 |
| 未跟踪文件（`git ls-files --others`） | 任何时候 | agent 新建还没 add 的文件 |

三个来源**并起来**判，任何落在写集外的路径都判 failed —— **越界检测不削弱**。

本片自己的提交怎么找：`git log --format=%H%x00%B%x00%x00 <base>..<head>`
解析出带本片标记的 commit，逐个算 `git diff --name-only <commit>^..<commit>`。

### ② 产物检查：`git ls-files` —— 状态判据（ADR-075）

判据：**产物在树上就在树上**（`git ls-files -- <path>` 能列出它）。

**为什么产物检查不能也用改动清单**：

改动清单的来源 ② 依赖提交历史 —— 切片被 squash 合并进主干后
（PR #91 那种），主干历史里没有 `feat(<id>): slice approved` 提交 →
认不出本片的提交 → 来源 ② 为空 → **产物检查全部落空**
→ **干净已提交树上必红**。

而本片规格的**验收标准 1 要求的恰恰是「干净已提交树上全部通过」**——
也就是说只用改动清单的实现**做不到规格要求的那一条**
（实测：v5 worktree 里四个套件的 missing 分别是 1 / 3 / 3 / 4，ok 全是 false）。

「产物在树上」是状态判据：合并策略（squash / rebase / merge commit）
都不影响它 —— 主干上的干净树与 worktree 里的进行中状态**判定一致**
（验收标准 2 要的也是这个）。

顺带解决的另一个问题：产物检查判成「在树上」之后，
判据就**不再依赖基点**，也就不会因为基点算错而误报。

### 与 zelto 运行时审计的关系
zelto 侧的写集审计（`core/sched/audit.ts`）在它自己的仓库里，本片只读不改它。
运行时审计回答的是「**本片 agent 改了什么**」（问题 ①）——
本片的 ① 与它同一口径。② 是验收测试**额外**要回答的
（产物在不在树上），运行时审计不承担。

## 需求
1. 四片的写集边界断言改成两半：
   - **越界检查**读**改动清单**（本片自己的提交 + 工作区未提交差异 +
     未跟踪文件三者并集），不再单看 `git diff --name-only`；
   - **产物检查**读**状态**（`git ls-files`）—— 判「产物在树上」。
2. 判据要能在**两种状态**下都成立：
   - 切片自己的 worktree 里（工作区有未提交改动）→ 绿；
   - 已提交的干净树上（主干、CI）→ 绿。
   不能靠「断言消失」或「断言改成永远为真」来达成。
3. 越界检测能力**不得削弱**：仍须拦下「本片改动了写集之外的文件」。
   验证方式：构造一个越界改动（一个写在写集之外的文件），
   断言检查逻辑判 failed。
4. 判据必须**确定性**：同一棵树、同一提交历史，重复跑结果一致
   （不依赖时间、不依赖网络、不依赖随机、不依赖环境变量）。
5. 四个套件用**同一套判据**（共用一份实现，不各写一份）——
   两份实现必然漂移，而漂移的方向恰好是「漏掉一条路径」。
6. 不得修改各片的**业务实现**（`examples/demo-agent-realtime/**`、
   `src/modules/**`）——本片只动验收测试。
7. 判据不得依赖**外部网络**或**模型**（验收测试必须是确定性计算）。
8. **产物检查不得依赖提交历史** —— 合并策略（squash / rebase / merge commit）
   不得影响判定。这是 ADR-075 的核心要求。

## 验收标准
1. 四个套件在**干净已提交树**上全部通过；验证方式：在已提交的主干树上
   逐个跑四个套件的验收命令，四条命令退出码均为 0
2. 四个套件在**有未提交改动**的工作区上同样通过；验证方式：制造一处未提交改动后
   重跑，退出码仍为 0（断言不因工作区状态而翻转）
3. 写集边界断言仍能拦下越界改动；验证方式：套件里的判据实现被一个越界场景调用，
   断言它返回「越界」
4. 四个套件共用同一套判据实现；验证方式：静态检查四份套件源码，
   写集边界那条用例都调用同一份共用实现
5. 判据是确定性的；验证方式：同一套件连跑两次，退出码与逐条用例结果一致
6. 业务实现未被改动；验证方式：本片提交的文件清单只落在验收测试范围内
7. 判据不触网、不调模型；验证方式：静态检查共用实现里没有 http/网络调用
8. **产物检查与提交历史无关**；验证方式：静态检查共用实现里，
   产物检查走的是 `git ls-files`（状态判据），不是提交历史；
   且在「提交历史里认不出本片提交」的树上，产物检查依然通过

## 风险
1. 提交历史里混进别的提交（基点算错）→ 越界误报 / 漏报；
   对策：以**基点 commit** 为起点算差异，基点取本片记录里的 `baseCommit`
2. 合并 commit（`Merge slice <id>`）把多片产物合在一起 → 差异里混进别的片；
   对策：按本片标记（trailer 或标题）过滤出本片自己的提交，逐个算差异
3. 切片还没提交时（agent 正在干活）跑验收 → 提交历史为空 → 越界检查看不到东西；
   对策：越界检查并看**工作区差异**与**提交历史**；产物检查用状态判据，
   与提交历史无关（所以不影响「产物在不在」的判定）
4. 改坏四个套件里的其它断言 → 对策：门禁②跑全套件，
   逐条用例结果与改动前比对（不只看退出码）
5. 产物检查用状态判据后，「产物在树上」不再区分「本片产的」与「别片产的」——
   对策：产物检查只回答「该有的产物在不在」（这是它的职责）；
   「是谁产的」由越界检查回答，两者分工不重叠
